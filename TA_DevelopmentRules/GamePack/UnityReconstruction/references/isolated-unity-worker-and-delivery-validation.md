# 独立 Unity Worker、并行保护与交付验证参考

> 类型：REFERENCE；适用范围：在已有工程中进行客户端资源与渲染还原、批量导入及 GPU 验证。使用前以目标工程、程序集、包解析和操作系统重新确认。规范来源为模块入口的 `UCR-ISO-01`、`UCR-VAL-01`、`UCR-VAL-02`、`UCR-VAL-03`；本页提供实现选择，不另建强制规则。

## 1. 适用场景

用户正在使用主编辑器，任务又需要导入大量资源、编译 Shader、加载多个场景、切换 Play Mode 或读取 GPU 输出。独立 Worker 可以把这些操作转到后台；但 Worker 的成功只证明它自己的宿主配置，仍需证明与目标工程兼容。

适用的交付目标是“能够在目标工程重新导入、实际播放，并解释差异和来源”。只生成文件、编译某几个脚本或截到一张正常画面，都不足以覆盖该目标。

一般离线编译方法见[离线 C# 验证参考](../../../ToolDevelopment/references/unity-editor-script-offline-compile-verification.md)。本页补充其在全工程验证、独立宿主和长期批处理中的边界；本次真实参数、命令与结果见[龙之剑 Profile](../Profiles/DragonSwordAwakening/character-rendering-reconstruction.md)。

## 2. 前提与依赖

| 输入 | 记录内容 | 用途 |
| --- | --- | --- |
| 工程身份 | Unity 版本、图形 API、颜色空间、目标平台、包版本及实际解析来源 | 防止验证了另一套宿主 |
| 修改前基线 | 现有资源与配置的路径、大小、SHA-256，关键 `.meta`、包锁定、场景和 Renderer 引用 | 判断本任务是否改到既有内容 |
| 任务边界 | 唯一资源根、允许修改集合、原始资料根、各角色清单 | 限制批处理和回退范围 |
| Worker 身份 | 独立工程路径、进程 ID、明确启动标志、专用日志、请求目录 | 区分用户编辑器和其他后台任务 |
| 验证计划 | 每项输入、执行入口、输出报告、通过条件和依赖项 | 避免反复重跑无关测试 |
| 磁盘与缓存 | 源包、解码数据、FBX/动画、GPU 数据、Library 的大小预估 | 避免解包成功但导入时空间耗尽 |

把大型原始资料和工具放入 Unity 忽略的目录，可以减少无意义导入；仍需检查目标 Unity 的忽略规则。忽略目录只是导入边界，不是只读保护、加密或自动备份。

## 3. 实现或排查步骤

### 3.1 先分配所有权，再运行并行工作

建议按资源与输出划分职责：容器/动画导出、GPU 取证、Unity 组装、文档与证据审计可以并行。多个进程同时提交同一 Worker 请求、保存同一场景或写同一报告则应串行。

| 可并行 | 保持串行 | 原因 |
| --- | --- | --- |
| 只读源码、不同抓帧、独立资产索引 | 同一 Worker 的 refresh、构建、播放、截图、退出 | Unity 场景、程序集和管线状态是共享的 |
| 不相交文件的实现 | 相同场景/材质/manifest 写入 | 后写入者可能覆盖前一修改 |
| 独立数值基准、文档草稿 | 编译后读取编译报告的集成审计 | 后者依赖前者完成并落盘 |
| 独立资源报告 | 汇总报告的哈希与交付 manifest | 证据文件尚在变化时，哈希快照会立即过时 |

只有实际独立的任务才并行；“两个脚本都是只读代码”不表示没有数据依赖。例如集成审计读取上一次编译结果时，与新编译并行会误报源码变化。

### 3.2 构建不会接管主编辑器的 Worker

可采用如下结构，名称由项目 Profile 确定：

```text
任务资源根/
  Runtime/ Editor/ Shaders/ Characters/ Scenes/
  CaptureData/ Validation/
  Evidence~/ Source~/
  Packages~/                 独立物理副本，不与主包目录共享写入
  Tools~/
    UnityWorker/             独立 Library、Temp、ProjectSettings
    Control/                 单写者请求与响应
    Worker.log
```

实现顺序：

1. 用明确的版本路径启动 Editor，保存非敏感启动参数、PID 和专用日志；后台进程隐藏窗口，避免抢焦点。枚举进程时只输出经过筛选的身份信息，不整段导出可能含登录令牌的命令行。GPU 验证保持真实图形后端，不以无图形模式替代。
2. Worker 仅暴露任务资产及显式列出的最小依赖闭包；非任务公共依赖优先用只读副本并核对身份、GUID 和哈希。允许用目录联接复用任务根时，先验证联接的绝对目标，认清 Worker 的资产写入会直接写回该根。
3. 管线包采用独立物理副本。共享包目录即使“原计划只读”，也可能被宿主自动序列化、更新或导入逻辑改写。
4. 不把主工程全部 Graphics/Quality 配置机械复制进去；这些配置可能引用未暴露给 Worker 的资产。需要的运行配置从清单重建并验证。
5. 自动初始化脚本先判断专用启动标志；正常主编辑器中不订阅轮询、不切场景、不自动保存。运行时代码不依赖 Worker 路径。
6. 保留可加载的空闲场景，操作完成后恢复它。只关闭属于本任务且进程身份匹配的 Worker。

若目标工程需要修改 URP 内部代码，先把包配置为受版本控制的本地来源，再做最小补丁；核对 manifest/lock、实际程序集、Graphics 和质量档的使用关系。若 RendererFeature 等局部扩展已能表达效果，无需为了“更彻底”而改管线。不能把本次的本地包版本、已有补丁或复制方式直接套入新工程。

### 3.3 把命令成功和异步任务完成分开

请求协议至少包含唯一 ID、方法、输入 manifest、输出位置和可选尺寸/帧数；先写临时文件，再原子移动为正式请求。单一控制者维护待执行状态，拒绝重复 ID 与未完成请求。

普通同步任务与 Play Mode 任务的完成语义不同：

| 状态 | 能说明什么 | 下一步 |
| --- | --- | --- |
| 请求文件写入 | 请求已排队 | 等待 Worker 消费 |
| 启动入口返回 | 方法已执行，可能只启动了异步操作 | 检查最终报告 |
| 报告更新且成功 | 这份报告约定的测试完成 | 核对来源、帧数和异常列表 |
| 退出 Play、恢复空闲场景 | Worker 可接下一个需要编辑状态的任务 | 再提交依赖请求 |

跨域重载可用宿主会话状态保存待执行数据，并在进入 Play 后恢复验证器。避免把一次性静态变量作为域重载后的唯一状态来源。

报告包括请求 ID 或输入哈希、开始/完成时间、实际版本、执行设备、场景、渲染帧数与最终状态。仅凭旧报告存在、控制台最后一行或 PowerShell 遗留的 `$LASTEXITCODE` 判定成功，容易把历史结果当成当前结果。

### 3.4 建立分层验证，不用一个布尔值包办全部结论

| 层级 | 主要输入 | 验证内容 | 不能代替的结论 |
| --- | --- | --- | --- |
| 原始资源 | 源包、映射、依赖索引 | 容器全部挂载、依赖闭包、导出清单与哈希 | 目标引擎可播放 |
| 导入资产 | 网格、bind、clip、贴图 | 通道、权重、路径、曲线、格式和 GUID | Shader 运算正确 |
| 数学/契约 | 独立原生样本 | 坐标、单位、曲线函数、惯量、状态映射 | 完整求解连续等价 |
| 同输入 GPU | 原 CB/SRV/历史快照 | 单 Pass/dispatch 输出、精度与分支 | 实时场景输入已正确生成 |
| 实时中间结果 | 实际骨骼和相机 | 深度、阴影、反射、motion、HDR、时域历史 | 最终所有动作视觉正确 |
| 连续 Play | Update/LateUpdate 后真实相机 | 真实渲染帧、动作切换、出生死亡、有限值、日志 | 每个未采样时刻均无视觉瑕疵 |
| 视觉抽样 | 约定帧的原图与重建图 | 朝向、构图、明显材质缺失、拉伸、持续上翻 | 同初态原引擎轨迹逐帧一致 |
| 工程集成 | 全工程编译和引用 | 脚本、包、场景、Shader 和现有内容保护 | Player 构建或所有硬件通过 |

数值断言应抓真实缺陷，例如单位重复放大、遗漏 draw、非有限值、曲线突跳。不要只测试实现内部恒等式，也不要用所有输入都经过同一错误转换的“自比较”当独立基准。

### 3.5 先完成一个代表角色，再把通过的契约推广

先选具有主要材质、头发、武器、反射、物理和展示动作的角色。用它贯通“源资源→原始 GPU 事件→Unity 输入→实际输出→报告”，再把相同实现应用到其他角色。

批量阶段保留逐角色差异，而非复制首角色参数：

- 身体与武器骨架、普通/特殊服装、可见部位与原三角分组。
- 实际阴影 caster、辅助 GBuffer、透明与反射绘制集合。
- 材质常量、灯光/背景/后处理参数及动画蓝图分支。
- 动作菜单、共享 Montage 与角色本地资源路径。

批量工具对缺失、歧义和未解析输入显式失败，不自动拿首角色材质、默认动画或猜测骨骼补齐。每个角色都有自己的最终验收项。

### 3.6 离线全工程编译与 Worker 集成证据

复用目标工程已经生成的编译响应文件，能够保存实际 define、引用、分析器与语言选项；前提是确认响应文件身份唯一且适用于当前平台。

1. 重新枚举当前可导入源码，排除 Unity 忽略目录，不继续使用旧响应文件里过时的源码集合。
2. 按真实程序集依赖顺序编译。存在 asmdef/asmref、特殊首轮目录或平台条件时，按实际程序集图分类；不能永远假设只有 Runtime 与 Editor 两个程序集。
3. 将输出 DLL、ref DLL、PDB、rsp、日志定向到任务临时目录，保持主 Library 与现有程序集只读。Editor 层引用刚生成的 Runtime ref，而不是旧 Library DLL。
4. 保存源码与只读输入的编译前后哈希、错误和警告数。新增修改后旧编译结果自然失效。
5. 编译完成后再做集成审计：主/Worker 包源码及解析来源、自动初始化守卫、运行时依赖、源码新鲜度、其他模块是否意外依赖任务命名空间。
6. 实际 Worker 另外确认已加载程序集覆盖新源码、Shader/Compute 编译、资源导入及 GPU 输出。无需为此强制刷新用户正在使用的主编辑器。

交付措辞分别写“目标编译上下文下离线全量通过”和“同版本 Worker 实际加载/渲染通过”；没有执行主编辑器刷新或 Player 构建时，不把它们包含在通过范围内。

### 3.7 避免验证器制造假故障或假通过

| 现象 | 可能是验证器问题 | 排查方法 |
| --- | --- | --- |
| 同一 Editor 帧内换骨姿态，后一张才更新 | 蒙皮矩阵按帧缓存 | 对临时测试对象检查逐 render 强制重算选项；与正常 Play 对照，验证后恢复，不任意修改生产性能设置 |
| 停止运动仍有 motion | 缓存时机、jitter混入或前帧姿态错误 | 分别测静止、只换jitter、骨运动、相机运动、停止；每项保持其他输入不变 |
| 报告只有有限值就判好看 | 断言只覆盖 NaN/Infinity | 另存实际图，检查幅度、轮廓、可见范围与稳定性 |
| 临时场景引用为空或多场景报错 | 空闲场景未保存、状态未恢复 | 先恢复已知空场景，再加载测试场景，最后执行清理 |
| 测试日志为空但图是黑的 | render 抛错后仍回读清空纹理 | 收集 Error/Exception/Assert，同时验证 draw/帧计数、有效像素与资源写入 |
| 颜色图正常，但临时目标写入有 Warning | 验证器只筛错误，没有覆盖失败的 GPU 目标绑定 | 按已确认的失败类型收集关键 Warning，核查实际深度/目标写入；不把专项筛选描述成全部 Warning 为零 |
| 角色末帧离屏 | 原动作大位移或测试中途切换动作 | 对照原 clip 位移、时间线与固定相机；保留该帧，不把它当完整外观验收 |
| 测试图正常而正式场景静止 | 使用捕获 RT、固定姿势或隐藏验证开关 | 检查正式序列化配置，实际运行并观察阴影/反射/历史随骨骼变化 |

对物理使用固定动画输入的多秒诊断，适合区分持续错误与转身惯性；它不等同真实运动，也不等同数学收敛。若要声称稳定收敛，另记录速度/能量或相邻窗口变化阈值。

自由相机验证还需独立检查几何关系。有限值、非黑、状态恢复和算法自身的恒等式都可能通过，而反射接触点仍错位；投影/宽高比的独立预期和实际图像审阅见[编辑态预览与自由相机适配](editor-preview-and-camera-adaptation.md)。

### 3.8 保护并行任务的成果

原工程基线变化时，先列出改变、缺失及来源，不自动回退“不是本任务计划的变化”。如果另一授权任务同时编辑，应将该任务的实际修改记录与路径、时点、哈希关联。

分别报告两个命题：

- 字面基线是否全部未变。
- 是否存在本任务未解释的修改或缺失。

前者为假、后者为否可以同时成立。不能为了让审计通过而忽略变化、改写基线或把所有差异都归给并行任务。发送其他聊天或外部协作提示遵守会话已授予的权限；已经自行修复的历史问题不再发送过时通知。

### 3.9 保存长期会话与退出诊断的不同结论

长会话日志常混有早期失败调查、导入、重编译、播放和退出。验收报告以请求、源码版本和时间窗口关联；不要从整份日志取最后一个错误作为当前失败，也不要删旧日志制造“从未报错”。

遇到退出时原生内存提示，可以依次做：

1. 保存原完整日志与提示行号，不改变生产代码。
2. 在同版本、图形后端和隔离工程中，添加宿主支持的分配诊断参数，做新进程空场景启动/退出。
3. 再用新进程执行最小代表角色的真实播放及资源清理，然后退出；记录调用栈是否出现、进程是否结束。
4. 检查代码直接 Native 分配与释放路径，再沿调用栈检查引擎/包/间接调用。没有直接分配不代表内部没有分配。
5. 区分具体分配警告、退出时按标签汇总的内存遥测、测试窗口的脚本异常。遥测总量不自动等于某段代码泄漏量。

短会话未复现只能缩小复现条件；没有来源调用栈时保留“来源未定位”，不能写“引擎问题已确认”或“问题已彻底修复”。

### 3.10 汇总证据时冻结顺序，避免循环哈希

建议按依赖关系收尾：

```text
冻结生产源码与资源
  → 全工程编译 → 集成审计
  → 必要的实际渲染/播放/健康与专项验证
  → 独立视觉审阅、文档与元数据
  → GUID/依赖审计、既有内容保护、资源终审
  → 最终 manifest（引用报告、场景与哈希）
  → 重新计算 manifest 引用哈希，确认无变化
```

依赖报告不要反向包含最终 manifest 哈希，避免两者互相更新。文档链接可以指向 manifest，资源审计检查其存在即可；若审计把文档字节也纳入哈希，先固定文档再生成最终快照。

并行任务可能在收尾时继续改动全工程源码，使刚生成的编译快照过时。先按路径、时点和实际修改记录确认来源，再重编受影响程序集及依赖它的程序集，按顺序更新集成审计和下游汇总；不回滚其他任务的有效修改。源码新鲜度变化本身不要求重跑全部 GPU 项，只有实际影响渲染输入、算法或验证条件时才补跑对应层级。若此次只整理文档，执行文档、链接与证据引用检查，不为了更新总结重新启动 Unity 或重演已通过的运行验证。

大型资源的完整哈希可以缓存，但记录首次计算结果、工具和时点。大小/mtime 一致只是一种后续增量检查策略，不等同重新验证全部字节；关键文件、发现变化的文件及高保真交付需求按风险重新计算。

交付清单建议包括：真实场景入口、原资源→导入物映射、工具版本、编译与宿主信息、实际渲染帧数、动作数、Shader/引用状态、视觉图、数值指标的范围、并行修改说明、已知边界、Worker 清理状态。

## 4. 风险与不适用边界

- Worker 资产联接不是沙箱；导入、保存和自动初始化都可能写回，操作范围由工具设计保证。
- 同版本包源码相同仍不能代表所有 Player/平台/图形设备表现相同；目标平台变化后重新验证受影响层级。
- 离线编译不能证明主编辑器已经刷新，正常播放不能证明退出路径无问题，截图抽样不能证明所有时间点无缺陷。
- Native API、蒙皮缓存和析构行为可能随 Unity 补丁、GPU 驱动改变，版本相关开关及诊断参数放在 Profile。
- 未解决问题应限定范围和后续可验证路径；不能通过降低物理权重、清空纹理、忽略异常或修改基线让数字通过。

## 5. 验证与回退

| 交付前检查 | 通过条件 | 失败时处理 |
| --- | --- | --- |
