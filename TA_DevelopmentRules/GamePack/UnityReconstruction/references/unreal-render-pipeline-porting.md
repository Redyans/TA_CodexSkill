# Unreal 渲染链到 Unity 的移植与故障排查参考

> 类型：REFERENCE；适用范围：有原客户端资源及可回放 GPU 捕获的角色展示效果移植；使用前提：按目标游戏版本、实际渲染路径、图形 API 与 Unity 管线重新验证。

## 1. 适用场景

用于恢复真实网格和动画驱动的材质、光照、阴影、反射、透明、粒子及后处理。目标是建立可追溯的输入与运行链，并定位差异首次出现的位置。单凭截图只能推导可见外观，不能恢复隐藏分支、原材质程序或捕获前完整历史。

规范来源为[模块入口](../README_Tech_UnityCaptureReconstructionRules.md)的 `UCR-EVD-01/02`、`UCR-AST-01/02`、`UCR-VAL-01/02/03`。通用 Shader 职责与管线扩展边界沿用 [Shader 开发模块](../../../ShaderDevelopment/README_Tech_URPShaderDevelopmentRules.md)的 `ARC-*`、`CMP-01`、`VAL-*`。本页不另立强制规则。

源资源准备见[UE 解包工具链](unreal-extraction-toolchain.md)，动作与物理见[动画与次级运动](unreal-animation-and-secondary-motion.md)，宿主与交付见[独立 Worker](isolated-unity-worker-and-delivery-validation.md)。本页方法来自[龙之剑 Profile](../Profiles/DragonSwordAwakening/character-rendering-reconstruction.md)；角色、事件编号、参数、版本、修复数量和实际误差都由该 Profile 及源工程专题承载。

## 2. 前提与依赖

### 2.1 建立四份互相关联的清单

| 清单 | 主要内容 | 支持的判断 |
| --- | --- | --- |
| 原资产身份 | 模型、骨架、纹理、材质、对象引用及哈希 | 当前输入来自哪个源对象 |
| GPU 事件契约 | draw/dispatch、输入布局、Shader、CB、资源视图/sampler、状态、输出 | 原帧真正执行了什么 |
| 目标运行计划 | 原事件到目标网格/材质/Pass/相机的映射、静态与动态输入 | 目标场景如何生产同类输入 |
| 比较计划 | 输入来源、阶段、尺寸、颜色域、区域、时间历史和容差 | 这项比较能证明什么 |

取证工具可以包括 RenderDoc Replay API、源字节码反汇编器、DXC/目标编译器、原始网格与纹理导出器、Unity GPU 探针及数值分析脚本。选型与安装入口见工具链参考；某个工具可反汇编并不表示它能正确反编译全部指令。

### 2.2 区分三种真值

- 原资产真值：原顶点字节、压缩纹理、曲线及序列化配置。
- 当前执行真值：捕获时真正读取的常量、变换、资源版本和分支；可能已受蓝图、实例或运行逻辑覆盖。
- 目标宿主真值：Unity 实际输入流、已加载程序集、GPU 输出与播放行为。

三者之间需要建立转换证据。不能因源材质参数看起来正确，就忽略 GPU 当前使用了另一覆盖值；也不能用 CPU 推算替代目标宿主真实蒙皮通路。

## 3. 实现或排查步骤

### 3.1 从最终目标向前追踪资源生产者

1. 定位 UI 绘制前的目标输出，确认参考截图是否取自同一时刻、同一颜色转换。排除 UI 是选择渲染范围，不是随意裁掉难以复刻的透明或粒子。
2. 向前回溯 tonemap/LUT、Bloom/flare、时域处理、透明、反射、光照、GBuffer、深度和阴影；实际顺序以捕获为准，不按通用 UE 流程假定。
3. 每个资源同时记录 Resource ID、事件号、子资源、视图格式、尺寸和当时内容哈希。同一个 ID 可被复用或在后续事件继续写入。
4. 对有前后版本要求的输出，分别保存写入前/后内容。记录 API 的事件定位语义，确认导出的是需要的版本。
5. 区分当前帧生成、上一帧历史和源静态资源。完整当前帧链不等于捕获了历史资源的生成过程。

推荐逐事件字段：原事件路径、draw/dispatch 参数、VB/IB 范围、实例与 primitive 身份、VS/PS/CS 哈希、输入布局、常量缓冲槽及字节、SRV/UAV/RTV/DSV 视图、sampler、viewport/scissor、混合/深度/剔除/stencil、输出格式与哈希。

以清单匹配原事件的多重集合，检查缺失、重复与额外项。主体、辅助缓冲、阴影和反射各自核对；主体三角齐全不表示武器阴影或反射辅助绘制也齐全。

### 3.2 先核对原输入通道，再移植材质数学

| 通道/数据 | 检查方式 | 典型错误 |
| --- | --- | --- |
| primitive 与材质分组 | 原三角角点、位置/UV/方向对应到 Unity 子网格 | 导出器合并同材质 primitive 后，旧索引计划指错三角 |
| 骨影响与 bind | 保留完整 bone map、同骨权重求和、实际宿主权重配置 | 字典覆盖重复 influence，或只保留最大四权重 |
| UV 与顶点顺序 | 按角点属性和原索引关系消歧，记录重排 | 仅按最近位置匹配缝边或重叠点 |
| 顶点色数值遮罩 | 对原字节、DCC 色层、FBX、Unity `colors32` 分段比较 | 数值经过 linear/sRGB 转换，描边或混合遮罩被放大 |
| 压缩法线/切线 | 按实际 VB 格式解码，使用原骨矩阵和 primitive 复算 | 把工具通用解码公式当成原 GPU 格式 |
| Morph 与尺度 | 比较各帧 delta、bind、actor 与导入根尺度 | 修复一条通道时重烘焙模型，破坏其他已验证数据 |

对有符号 8 位 SNORM，标准解码形状为 `max(v / 127, -1)`，其中 `v` 是有符号整数；只有实际 GPU 输入格式确认如此才适用。某个导出器采用的偏移无符号解码可能并不等价。归一化、量化、插值和顶点解码分开比较，不凭视觉方向猜公式。

顶点颜色究竟是显示颜色还是数值数据，由原 Shader 消费方式决定。原始 RGBA8 可得时从原字节恢复；用逆 gamma 近似处理导出结果会引入量化及实现差异。若重叠顶点位置/UV相同但颜色不同，需要额外的已验证通道或索引关系消歧；仍歧义则拒绝生成。

正式模型已建立绑定和索引契约后，可选择只修派生 Mesh 的目标通道。应用前检查来源哈希、顶点数与顺序保护；应用后比较位置、全部 UV、索引、权重、bindpose、Morph、非目标颜色/方向等不变量。重新导出源模型也是方案，但需要连同绑定/primitive/材质计划整体重验，不能混用新模型和旧映射。

### 3.3 用实际 GPU 探针定位 TBN 手性

从原 VS 指令确认切线、法线在哪一步归一化、何时乘骨矩阵及 primitive、是否移除尺度。分别观察原 PostVS 中 T/N 长度、方向和手性，避免把归一化误差与坐标反射混成同一问题。

目标探针沿正式相同 draw 路径输出浮点 T、N、B 及符号信息，使用同一 VP、深度和真实蒙皮输入。选择三角内部像素，通过透视正确插值与原 PostVS 比较；轮廓、遮挡和深度不匹配的采样单独处理。

CPU `renderer.localToWorldMatrix`、GPU 对象矩阵、预蒙皮顶点流及 `GetOddNegativeScale()` 不保证具有相同镜像表示。宿主可能将镜像吸收到蒙皮顶点流，导致 GPU 对象矩阵符号与 CPU 不同。先测实际路径，再决定是否传入原 renderer 的独立符号；静态与蒙皮对象分别验证。

不能由一次符号差异推导“全局翻转副切线”或“所有 Unity 都如此”。CPU `BakeMesh` 是另一个输出通路，可帮助检查几何，但不能替代正式 GPU 探针。

### 3.4 将 Shader 字节码转换为可验证的目标程序

自动生成的 HLSL 先作为数据流草稿。对 DXIL/SSA、DXBC 指令或中间表示，保留原寄存器/变量对应关系和 source offset，便于回查分歧。

| 语义 | 移植关注点 | 检查方法 |
| --- | --- | --- |
| 数值类型 | int/uint/float、位重解释与数值转换、符号扩展 | 原位模式与边界输入，区别 `asuint` 和数值 cast |
| 运算顺序 | 饱和、clamp、除法、FMA、精确常量位模式 | 首次出现差异的中间值或局部 GPU 输出 |
| 分支与比较 | 有符号比较、条件选择、NaN 行为、分量访问 | 覆盖边界值，不能只用一个正常像素 |
| 资源采样 | view 格式、sRGB、mip、LOD/bias、filter、wrap、comparison | 保留原 mip/face，分别验证解码与采样 |
| 插值与导数 | 透视/nointerpolation、ddx/ddy、隐式LOD | 在真实三角与同样采样条件下比较 |
| 输出 | MRT 格式、alpha、discard、深度偏移及深度语义 | 检查全部附件与深度，不只看最终 RGB |
| 精度 | 原生 half、min16、float、编译器重排 | 相同输入跨后端 GPU 比较，记录误差尾部 |

先用离线目标编译器检查语法和不支持特性，再由 Unity 实际编译及 GPU 回读证明运行路径。原 Shader Model 与目标后端精度不同，添加 `precise` 或显式中间变量只能作为有证据的局部修正；它不保证整个程序逐 bit 相同。

使用共享计算内核与独立绑定描述承载共用逻辑；逐材质差异保留在来源计划中。优化、合并表达式或删分支放在正确性基线之后，通过同输入回归证明没有改变行为。

### 3.5 按原生产/消费契约组织 URP Pass

优先用专用 RendererFeature/RenderPass、材质与相机配置恢复源链。标准 URP 能表达的部分按既有 Shader 规则复用；源延迟链与默认 URP 光照不同且有证据时，独立实现所需阶段，并说明输入和输出职责。

| 阶段 | 先证明的契约 |
| --- | --- |
| 预深度 | 与主体一致的几何、蒙皮、alpha/WPO 和相关深度偏移 |
| 主 GBuffer | MRT 编码、精度、写掩码、原材质分组与当前变换 |
| 辅助缓冲 | 深度比较函数、是否依赖先前深度、写入通道与覆盖范围 |
| 阴影 | 原 caster 集合、相机、cull、bias、投影与采样 resolve |
| 延迟光照 | 实际读取的 GBuffer/深度、光源变换、SH/环境、通道及曝光域 |
| 透明与合成 | premultiplied/straight alpha、排序、深度、背景和累积规则 |

辅助 draw 使用 `Equal`、主体使用另一深度测试是合法契约，不能统一改为“更容易画出来”的比较函数。检查空白像素是原本应空、没有覆盖还是状态错误，避免降低深度约束掩盖重复绘制。

只在局部扩展不能表达需求且证据充分时修改管线包。先使用受控本地包来源、保存版本与最小补丁、验证实际解析和回退；不要直接修改包缓存或为无关相机改变全局流程。当前案例是否改过管线以 Profile 为准，不能因存在本地包就认定是本任务修改。

### 3.6 将实时阴影和反射与原输入回放分开

阴影排查依次比较 caster 几何、shadow depth、偏移、投影、比较采样和屏幕合成。普通武器与独特武器可能共享主体外观却使用不同 caster；按实际源事件核对，不能按对象是否显眼决定是否导出。

实时反射需要本帧真实几何、正确的反射 view/projection、剔除方向、专用输入和其自己的历史。源反射的 alpha 有时表示覆盖，有时表示逆覆盖，不能套用普通透明材质含义。反射 lighting channel、辅助深度条件和复用阴影也分别取证。

需要 CPU 烘焙蒙皮几何时，明确 API 返回的空间和尺度、是否已含导入单位、之后还要乘哪个矩阵。对 `BakeMesh` 的缩放选项用原模型、已知骨变换和世界尺寸实测；某项目正确的布尔参数不是跨项目的通用答案。

反射 history 与主相机 history 不能因尺寸相同而共用。相机、分辨率、profile 或资源身份变化时按原语义初始化/失效；记录释放与恢复边界。捕获反射 RT 可供独立回放验证，正式配置则检查生产者，并在角色运动时观察反射对应变化。

### 3.7 分解后处理颜色域与像素坐标

先建立“资源格式/视图 → 读出的数值域 → 当前运算 → 写入视图 → 最终显示”的表，分别标注 linear、sRGB、HDR、pre-exposed 与显示编码。截图为 PNG 不说明它保存的是线性数值还是已编码显示值。

1. 从实际指令读取的位置确定曝光、pre-exposure、LUT、Bloom 参数；蓝图默认只说明可能的初值，运行覆盖另查。
2. 单独验证复制/缩放、阈值、降采样、各高斯核、bokeh/ghost/flare、合成、LUT/tonemap、锐化与暗角，再串完整链。
3. 保留各中间 RT 的格式和舍入边界。换成更高精度格式可能改变结果，不必然更接近原画面。
4. 记录 LUT 尺寸、布局、输入映射、半 texel、插值和输出域；已有源 LUT 包含调色或 tone mapping 时，避免再叠默认后处理。
5. 检查最终显示只进行了约定次数的颜色转换和 Y 变换。比较时从同一颜色域读取，不同时混用线性 HDR 数组与已编码截图。

原生内部尺寸与最终窗口尺寸分开。材质屏幕采样、jitter、bokeh、粒子像素覆盖和后处理偏移按源契约计算，最后再缩放到窗口并保持比例。用多个输出尺寸测试原生中间缓冲是否一致，并独立验证最终双线性与留边；不要仅靠“画面没拉伸”判定采样正确。

### 3.8 恢复 motion、jitter 与 FSR 时域数据流

先用 Shader/CB 布局确定实际时域算法和工作模式，不凭捕获文件名或模糊边缘判断版本。将 motion、depth、颜色、reactive/transparency、曝光、各历史和 dispatch 顺序逐项映射；只有实际用到的分支才作为已恢复范围。

motion 契约包含前后帧方向、坐标单位、UV 原点、是否含 jitter、世界/相机矩阵和分辨率缩放。原算法若要求无抖动运动，按已确认方向使用两帧无 jitter 投影；不能随手选择 `current-previous` 或 `previous-current`。

骨骼角色的前帧位置来自前帧实际蒙皮/世界状态，而非只保存对象矩阵。WPO、alpha discard、描边与条件深度偏移也可能影响有效覆盖和输出深度。当前和上一帧的法线/位移输入需要保持源语义。

最小运动矩阵包括：静止、仅 jitter、仅骨运动、仅相机运动、运动后停止。逐项检查运动像素数与幅度；同一 Editor 帧反复手动 Render 时先排除蒙皮缓存时序，详见 Worker 参考。

算法移植后先用原颜色/深度/motion/history 做单 dispatch 同输入验证，再使用真实场景生成的输入测试连续帧。保存中间输出、非有限值、MAE/RMSE、最大误差、分位数及超阈值像素。只有最终平均差小，不能证明对阈值敏感的分支或少数高误差像素正确。

不同 API 的 native-half、min16 和 float 的执行差异需要单独量化。逐字符复写同一个公式并不保证运算精度相同；原 SDK 头文件也需与实际指令、常量布局和分支核对。

### 3.9 从 Niagara 原规则恢复生命周期

捕获到的粒子 quad 可以验证 renderer 输入，却不能恢复整个 emitter。持续模拟还需系统/emitter 状态、spawn/update VM、literal、数据集/外部函数绑定、组件覆盖、曲线、噪声场、owner 变换及积分顺序。

建议先解释原字节码构造独立数值 fixture，再移植到目标运行时；记录已支持/未支持操作码与常量偏移，而不是遇到未知操作直接返回零。实际组件覆盖可能与原 asset 默认颜色、尺寸、出生率不同。

重点测试发射小数余量、帧内出生时间、跨循环、大/小时间步、停止发射、死亡边界、随机数消费顺序，以及速度和位置更新顺序。噪声场原始数据、bounds、wrap 和插值单独验证。Sprite 朝向、UV 翻转、颜色、旋转、尺寸和像素覆盖继续使用原 GPU 属性做 renderer 验证。

原系统非确定性且未保存 RNG 状态、寿命、初始颜色、粒子 ID 或余量时，显式新 seed 可以产生可复现的新模拟，不能声称延续捕获进程的历史。粒子规则/渲染器通过、生命周期通过和逐粒子原轨迹一致是不同结论。

### 3.10 用差异首次出现的位置决定下一步

| 现象 | 优先检查 | 修正与验证方向 |
| --- | --- | --- |
| 描边比原版厚，但主体位置正确 | 顶点遮罩原字节、导出颜色转换、VS 位移输入 | 修数据链，再比描边；不先缩小全局描边宽度 |
| 镜像蒙皮高光方向反了 | 实际 GPU TBN 与 CPU/GPU 符号 | 同路径探针及原 PostVS；静态/蒙皮分别处理 |
| 法线只有小角度残差 | 原 packed format 与解码公式 | 原压缩字节替换唯一解码变量进行复算 |
| 身体正确但阴影少一部分 | 独立武器/辅助 caster 集合 | 原事件与保存场景多重集合及 shadow depth |
| 反射尺寸离谱 | 烘焙几何单位、导入根和重复世界变换 | 固定已知骨姿态验证几何空间 |
| 反射轮廓或透明边缘有方块 | alpha含义、辅助Equal、history归属 | 比较反射附件、覆盖与专用前帧历史 |
| 平均亮度正常但高光/暗部不同 | pre-exposure、LUT域、RT精度、重复调色 | 同输入分阶段比较，避免整图拟合曝光 |
| 窗口改变就变亮或粒子大小变 | View尺寸、屏幕偏移、最终缩放 | 固定原生内部尺寸，多窗口原生缓冲哈希对照 |
| 静止仍拖影或速度不为零 | jitter、前帧蒙皮、相机历史、缓存 | 五种运动测试，再接入真实Play |
| 粒子一开始像，之后全错 | 只推进捕获速度、缺spawn/death/VM覆盖 | 原生命周期fixture与停止后的完整死亡验证 |
| 固定Pose很好但运行异常 | 固定验证配置混入正式场景 | 核对正式输入生产链与实际动作、反射、历史 |
| 全图MAE很低却人物脸错 | 背景稀释、局部/极值未报告 | 角色内区、轮廓、背景及最大差分别观察 |

## 4. 风险与不适用边界

- 当前帧资源不提供全部过去状态；单帧抓帧不能独立证明完整模拟、temporal history 或动态输入逻辑。
- 同输入 Shader 比较通过只说明受测输入和分支；正式场景可能仍有错模型、少draw或错误历史。
- 源资源定义为静态的环境或背景可以保留静态表示；不能用目标截图替代应由真实模型/灯光产生的结果却宣称实时还原。
- 原生零切线、零向量归一化或其他退化值若在目标使用有限后备，记录数量、通道及视觉影响，将其作为明确替代边界。
- 对压缩格式、DCC 转换、GPU 蒙皮、图形 API 和半精度的结论限定于验证过的版本与路径；不要全局修改数据以适配一个样本。
- 固定Pose关闭目标时域而原捕获含历史的比较属于诊断，不能标为相同历史逐像素验收。不同时间JPG/RDC也同理。
- 本页没有给出适用于所有游戏的光照、曝光、重力或容差默认值；这些由原数据和目标任务范围决定。

## 5. 验证与回退

证据顺序为“源字节/对象 → GPU事件契约 → 目标输入/状态 → 同输入模块 → 实时中间缓冲 → 最终颜色 → 连续播放与视觉”。每层保留输入哈希、版本、API、原生/输出尺寸、时间点、测试条件和失败项。

| 验证 | 有效通过条件 | 进一步限制 |
| --- | --- | --- |
| 源模型通道 | 按原映射逐字节或明确容差，非目标数据不变 | 不替代实际GPU蒙皮 |
| 原事件覆盖 | 各阶段无遗漏、重复、错误绑定 | 不替代Shader正确性 |
| 同输入GPU | 约定输出均有限且误差在已解释界限内 | 不证明当前场景输入生成正确 |
| 实时缓冲 | 原生几何、阴影、反射、motion和history按契约变化 | 不保证全部动画时刻 |
| 最终图 | 统一颜色域，分别报告角色内部、轮廓透明、背景与全图 | 掩码定义、排除像素及历史差异公开 |
| 连续运行 | 实际渲染帧数、动作状态与日志完成，图像抽样无阻断 | 不把数值finite当作视觉等价 |

比较至少保留 MAE、RMSE、最大通道误差、分位数、超过阈值的像素数及对应图。原图自比较应为零；翻转、裁剪、配准、重采样、Gamma等处理都写入比较方法。另存原始未处理输出，避免后处理图片把证据变化隐藏掉。

回退按模块恢复源码、绑定计划与派生资产，保留原始证据和已验证模型身份。新Shader/导出器修正先做最小fixture，再扩大到受影响角色和阶段；共享实现改变后检验所有实际消费者。没有新变化或未决风险时无需反复运行全部检查。具体命令及现有验证入口从[项目 Profile](../Profiles/DragonSwordAwakening/character-rendering-reconstruction.md)定位原工程功能文档，不在规则库维护第二份生产实现。
