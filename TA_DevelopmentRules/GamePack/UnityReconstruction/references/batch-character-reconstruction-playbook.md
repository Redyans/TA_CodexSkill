# 批量角色渲染还原与光照验收参考

> 类型：REFERENCE；适用范围：从一个已贯通的 Unity 角色展示场景推广到多角色，并沉淀可迁移的制作和排错方法。使用前以目标工程、源包、抓帧和当前需求重新验证。规范来源为模块入口的 `UCR-EVD-*`、`UCR-AST-*`、`UCR-ISO-01`、`UCR-VAL-*`，本页不另设强制规则。

## 1. 适用场景

已有模型、动作、材质和展示环境的还原基线，需要继续解包新角色，复用公共 Shader、背景、地面、光照与后处理。也适用于“画面大体正确，但局部偏暗、透明、缺附件或换动作后失效”的排查。

完整制作流程是：输入与验收口径 → 源资源依赖 → GPU 实际路径 → 可编辑资产 → 共享渲染实现 → 角色差异 → 单角色验证 → 批量推广。共享实现解决重复劳动，角色差异清单决定每个新增角色还需要做什么。

| 要解决的任务 | 配套资料 |
| --- | --- |
| 从零解包、模型/贴图/动画导入、Shader 与管线适配 | [Unity 资源与抓帧渲染复刻工作流](unity-asset-and-render-reconstruction-workflow.md) |
| 已出现具体画面或宿主故障 | [RenderDoc 验证与故障排查](renderdoc-validation-and-troubleshooting.md) |
| 不干扰主编辑器的后台处理、状态恢复与交付 | [独立 Unity Worker 参考](isolated-unity-worker-and-delivery-validation.md) |
| 首个角色的完整实现、精度报告与工具版本 | [依盖之书基线 Profile](../Profiles/BookOfYog/linglong-showcase-reconstruction.md) |
| 批量过程中的实际修正、近似方案与遗留问题 | [依盖之书批量经验与状态](../Profiles/BookOfYog/batch-reconstruction-lessons-and-status.md) |

## 2. 前提与依赖

先确定验收问题，避免使用一种证据回答另一种问题。

| 验收目标 | 主要观察 | 能得到的结论 |
| --- | --- | --- |
| 光照与整体观感 | 主光方向、肤色明暗、材质层次、金属反射、阴影与脚底接触、环境色、曝光和 Bloom | 在约定镜头和姿态下观感接近；不要求每个像素相同 |
| 同输入算法 | 同一 CB、纹理、sampler、格式、历史输入下的 Pass 输出 | 该算法在给定输入下的数值一致性 |
| 动态可用性 | 动作切换、身体/武器独立动画、附件跟随、纹理贴附、实时阴影/反射、历史更新 | 已覆盖动作和时间范围内可播放 |
| 工程交付 | 正确包来源、编译、资源引用、场景重开、报告与可复现入口 | 当前宿主能够加载并重现约定结果 |

光照验收可以容忍同帧姿态难以精确匹配、局部纹样或特效相位差异，但明显缺肢、错误透明、严重拉伸、丢武器仍应单列缺陷。暗部接近参考并不能抵消几何或透明链错误。

工具按输入格式和待解决的问题选择，不因某工具流行而增加转换环节：

| 工作 | 优先能力 | 核对点 |
| --- | --- | --- |
| UnityFS 与对象引用 | UnityPy、Unity 原生 AssetBundle API | 源引擎版本、依赖闭包、PathID、实际可加载性 |
| GPU 实际绘制 | RenderDoc Replay API、Pixel History、顶点输入/阶段输出 | 事件、资源版本、视图格式、完整 Shader 阶段 |
| DXBC 转译 | 反汇编、反编译器、目标 GPU 编译/回读 | swizzle、整数重解释、插值、采样和状态 |
| 原动作持久化 | 原生动画 API、必要的压缩曲线解码 | 时长、key/切线、路径、真实播放 |
| 运行行为定位 | 必要的托管/原生代码分析工具 | 只有资源与抓帧不能解释行为时才扩大到代码 |
| 批量验证 | 同版本 Unity Worker、Python 图像/结构化数据处理 | 宿主身份、请求完成、报告新鲜度 |

FModel 面向 Unreal 资源工作流；标准 UnityFS 任务先使用 Unity 工具链。Python 包属于某个解释器，安装前检查该解释器的 `sys.executable`、版本和导入能力。RenderDoc Python 模块依赖它的发行包及运行宿主，普通 Python 导入失败不自动意味着需要重装 RenderDoc。

## 3. 实现或排查步骤

### 3.1 先证明共享边界，再开始批量

把首个角色做成可复现基线：场景、工具版本、源资源清单、实际 Shader、光照/后处理配置、正式预览与已知限制均能定位。新角色先比实际 draw 与程序签名，再检查动态输入。

| 内容 | 常见复用方式 | 每个角色仍需检查 |
| --- | --- | --- |
| Shader 算法与后处理程序 | 复用相同字节码对应的实现或已验证家族 | 变体、常量布局、纹理、sampler、Render State |
| 光照、天空、地面和水面 | 相同场景语义与输入下复用公共资产 | 灯光常量、对象范围、阴影生产者、反射相机与资源 |
| 模型和骨架 | 从角色依赖清单导入 | 骨顺序、bindpose、顶点通道、子网格、附件 |
| 材质资产 | 按角色/抓帧单独持久化 | Renderer 的实际槽位及每条 draw 的绑定 |
| 动作 | 同一来源的动作可共享原数据 | override 关系、骨骼路径、独立武器相位、循环语义 |
| 截图、屏幕阴影、GPU 后变换网格 | 用于当帧诊断 | 不承担动态功能；相机或姿态改变后有效性下降 |

字节码哈希相同只证明程序相同，不证明输出相同。复用灯光数值也不代表另一体型的自阴影相同。一次只推广已验证的那层，避免把首角色的事件号、矩阵、相位或历史纹理作为全局默认值。

### 3.2 建立角色与抓帧两级目录

同一文件夹可能含多个 RDC，同一角色也可能有不同皮肤和抓帧；稳定标识宜包含角色/皮肤和抓帧身份，不能只用文件夹编号。

```text
任务资源根/
  Characters/<Character>/
    Animations/                    原始展示/战斗/武器动作及来源映射
    Models/                        可编辑模型、骨架和预制体
    Cases/<CaptureId>/
      Materials/                   本帧材质绑定与覆盖
      Textures/                    本帧使用的纹理或共享引用
  Environments/<Showcase>/          背景、地面、水面和环境资产
  Shaders/ Runtime/ Editor/ Settings/
  Scenes/                          实际可打开的展示场景
  Evidence/                        输入、依赖、事件和资源映射
  Validation/                      正式预览、分层报告和参考图
  Tools~/                          提取器、工作副本、诊断图、Worker
```

这是推荐布局，不要求无证据搬动已用资产。移动资产时保持 `.meta` 身份和消费者引用。共用实现集中维护，角色专属覆盖留在角色层；大型包、缓存和工具放 Unity 忽略目录，避免导入无关内容。

### 3.3 用绑定清单连接解包资源与真实画面

解包索引回答“有哪些对象”，GPU 抓帧回答“这一帧实际画了什么”，Unity Renderer 回读回答“现在用的是哪个资产”。三者连接后再改材质。

建议保存一张表，字段包括：Case ID、Renderer 层级路径、Mesh/Submesh、材质槽索引、材质 GUID/路径、原 draw、Shader 阶段哈希、纹理槽及资源、sampler、关键常量、Blend/Depth/Cull/Stencil、对象矩阵。

事件号的大小与 Renderer 材质槽顺序没有必然关系；Mesh/材质名称相似也不能证明绑定。多余材质槽可能确实触发叠加绘制，不能看到槽位数大于子网格数就删除。先逐槽隔离，确认像素贡献和原始绘制集合。

找不到可见附件时，按“原图像素贡献 → draw → IA 网格与对象矩阵 → 源 prefab/模块 → Unity Renderer”定位。附件审计中的候选仅表示可能缺失，仍可能是环境平面、已恢复 draw 或叠加层。

### 3.4 按数据流恢复材质，先检查采样和顶点阶段

局部颜色错误时，先核对贴图输入与采样，再改光照。保留压缩块、mip、sRGB view、法线编码及 sampler 信息，PNG 仅承担预览时不要将它当作完全等价输入。

`Repeat`、`Clamp`、`Mirror`，过滤方式、LOD 和纹理视图是独立事实。同一贴图被不同 sampler 使用时，直接改共享 `Texture.wrapMode` 可能影响别的材质；按原 draw 的语义选择显式 sampler 或独立纹理资产，并回归所有消费者。负 UV 下 `frac(-0.2)=0.8` 与钳制到 0 的结果完全不同，但手工 `frac` 又可能改变导数/mip，不能直接替代原 Repeat 采样器。

细分路径按 IA → VS → HS → DS → PS 检查。恢复细分因子和三角形数量后，还要核对 DS 输出的每个插值分量。`TEXCOORD0.zw` 可能是 alpha 或其他控制量，不能按名字一律解释为 UV。若 PS 乘上其中一个分量再执行 `discard`，错误插值会让本来存在的几何消失。

后变换顶点用于证明当前 draw 的姿态、拓扑或插值，通常不具备源模型的绑定和动态语义。把它用于静态对照时保持明确命名，动态替换继续恢复源 Mesh、骨架和阶段算法。

### 3.5 恢复动画与附件，而不只保存一张姿态

先从展示状态、Controller 和 override 关系找到真正使用的 clip，再提取其他可替换动作。多个槽可能最终指向同一个 clip；身体和武器可能由独立 Animator 驱动。

对“文件存在但不动”的动作检查运行时压缩流、编辑器曲线、时长、binding hash、骨路径和实际位移。必要时从源多项式、key 时间和值/切线重建 Hermite 曲线，保留未映射项；不要只靠固定帧率重采样掩盖路径丢失。

刚性附件在已知骨姿态下可由 `M_local = inverse(M_parentWorld) * M_captureWorld` 求局部变换。先检查矩阵约定、负缩放、父级和角色世界原点，再保存挂点；有 shear 时不要假定任意矩阵都可无损分解成 Unity TRS。随后更换动作，观察附件是否跟随及局部变换是否漂移。蒙皮附件不能仅靠刚性挂点替代绑定。

相位搜索只在相机、挂点、几何和采样已正确时使用。静态物件变换错位通常不能靠调整人物动画时间解决。

### 3.6 以局部问题决定排错顺序

| 现象 | 优先排查 | 暂不作为正式修复 |
| --- | --- | --- |
| 全图偏亮、暗部抬升或整体色调错 | 色彩空间、曝光、LUT 输入域、重复 tonemapper | 修改所有角色材质颜色 |
| 仅一个部位偏暗或纹样成横条 | 实际槽位、UV、sampler、法线、DS/PS 插值 | 提高主光或全局曝光 |
| 一条腿或薄片消失 | 隔离 Renderer、纯色标记、Cull/Depth、alpha/clip 和细分阶段 | 直接认定网格未导出 |
| 武器可见但位置/朝向错误 | 对象矩阵、骨挂点、独立 Animator 与相位 | 在多角色公共相机上补偿 |
| 单个轮廓/效果完全没有 | Pixel History、draw 集合、附属 prefab 依赖 | 用相似名字的资产顶替 |
| 动作切换后阴影和纹样不跟随 | 捕获纹理、世界空间程序纹理、固定对象/VP 常量 | 把静态截图通过扩展为动态通过 |
| 改第二个对象才出现黑图 | 场景、骨缓存、RenderTexture、材质实例、时域历史 | 把有污染的后续图当原算法证据 |

先对比明暗变化出现在哪一层：Albedo/法线 → 无阴影照明 → 阴影合成 → HDR → 后处理。强制全亮、纯色标记、隐藏某层、取消深度测试都是诊断手段，判断它们改变了什么；它们本身不证明原始材质算法已恢复。

### 3.7 让一次诊断只改变一个可解释因素

每组 A/B 从相同已保存场景开始，设置明确时间与相机，重建必要历史，然后只改变一个因素。正式场景、试验材质和诊断输出分开命名；临时材质实例及 RT 在 `finally` 中释放并恢复原引用。

重开场景能减少状态继承，但不一定清除静态字典、全局 Shader 参数或外部 history 缓存。仍异常时检查状态所有者，必要时用新的专用 Worker 进程复现。同一场景内先隐藏 A、再隐藏 B 的输出可用于发现候选，最终解释再用独立重开复拍。

相位搜索可做正序、倒序与同一时间重复采样。如果同一时间输出不同，先定位骨缓存、未绑定通道、物理历史和 TAA 状态，再讨论哪一相位更接近。场景重开与真实连续播放分别覆盖不同命题。

### 3.8 把光照验收做成逐角色闭环

1. 按稳定 Case ID 排序，读取该角色参考和已保存的正式预览，确认不是上一角色或另一帧。
2. 检查身体完整性、面部受光、皮肤亮暗与冷暖、衣料/金属层次、头发和透明边缘、阴影/接触、背景地面及后处理。
3. 只针对当前角色最明显的问题回到对应数据层；公共设置已有证据通过时优先查角色差异。
4. 修改后独立复拍，保存变更、证据、近似项和未验证范围，再继续下一角色。
5. 输入损坏的角色记录失败原因并跳过；保留原件，不把修过文件头等同恢复了压缩数据。

整图 MAE 常被大片相同背景稀释。数值可定位回归，角色局部图和视觉判断用于光照目标；不把微小误差继续优化成无限的像素对齐任务。缺失身体等可见错误仍单独处理或登记未解决，不用整图均值宣布通过。

### 3.9 有意识地限制近似方案

当证据不足而当前只需固定展示时，可以记录受限近似，但为它保留明确作用范围、默认关闭开关、原始输入、撤销方式及未来替换条件。程序纹理使用哪种坐标空间，决定它跟随物体、骨骼还是世界；直接乘暗最终 RGB 会连带改变高光、间接光及材质层次，并非只修改 Albedo。

经验文档分别写“症状有所改善”“根因已确认”“原实现已恢复”“动态已验证”。四者并不等价。假设被后续实验否定时保留否定证据，并撤回先前的根因判断；不要继续叠补丁把错误来源藏起来。

### 3.10 让工具链可重复运行并减少人工干扰

工具按读取、提取、生成、导入、修正、验证分步，前一步的清单是后一步的输入。为输出保存稳定 ID、输入哈希、生成器版本/参数和报告位置；从任一步重建前确认哪些手工覆盖会被覆盖。

同一 Unity Worker 的 refresh、编译、场景写入、渲染和异步播放串行执行。隐藏窗口与真实 GPU 后端可以避免接管鼠标；启动命令返回只表明进程或请求已开始，结果 JSON 和预期输出的新鲜度才说明对应操作完成。

搜索大型工程先限定目录和扩展名，再解析 JSON 取必要字段。避免对二进制资产、巨型文本 `.asset`、Library、PackageCache 和压缩数据的单行 JSON 执行无范围全文搜索。先验证已知工具路径和解释器，缺失时再安装所需能力，不反复扫描整盘。

## 4. 风险与不适用边界

- 此流程不把首角色的原生纹理校验、TAA/AO 同输入结果或编译通过自动继承给其他角色。
- 相同场景模板与光照参数可以节省制作时间，不能省略当前 draw、绑定和可见完整性检查。
- 捕获阴影、固定姿态网格和世界坐标纹理可能让单帧接近，不能据此保证换动作、换相机或移动后的效果。
- 通用排查顺序不是个案根因。没有独立对照和输出证据时，Domain、sampler、alpha 等只能写成候选。
- 修改 URP 时遵循目标项目包管理契约，先本地化再改；优先使用已足够表达需求的局部扩展。不把某项目的 Junction 布局当成所有平台做法。

## 5. 验证与回退

| 修改类型 | 有意义的最小验证 | 回退与记录 |
| --- | --- | --- |
| 当前材质或 sampler | 独立重开当前角色、局部和整体预览；核对共享消费者 | 恢复材质/纹理设置，保留原始绑定与诊断图 |
| 共用 Shader 或生成器 | 目标宿主编译，受影响代表材质和依赖角色回归 | 恢复自有修改；防止重新生成覆盖已验证特例 |
| 附件变换或动作 | 固定姿态矩阵检查，加若干实际播放时刻 | 保留原 prefab 和 GUID，分开记录静态/动态结论 |
| 公共后处理或管线 | 包解析与编译，中间缓冲及代表场景；按影响扩大回归 | 恢复配置备份与本地包入口，保留失败日志 |
| 只整理经验文档 | 事实/来源、证据时点、链接、编码、ID 和 `.meta` | 不为了写总结重新生成资产或沿用旧报告冒充新验收 |

交付记录至少说明场景、参考与预览、验收口径、实际执行的检查、近似方案和动态边界。报告时间或源码发生变化时，旧结果仅保留为历史阶段；哈希能证明读到了哪份文件，不能替代运行或视觉验收。已有证据足够且输入未变时，不为扩大检查数量重复运行无关测试。
