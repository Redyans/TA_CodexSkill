# 旧 Unity 工程、依赖与资源入口恢复参考

> 类型：REFERENCE；适用范围：源码、资源备份和构建产物混放，缺包、缺配置或依赖定制引擎的 Unity 工程。
> 本文提供迁移方法，不预设 Unity/URP 版本。项目路径、兼容宏、真实修复与限制见 [AlphaAce Profile](../Profiles/AlphaAce/project-and-weapon-showcase-recovery.md)。

## 1. 适用场景

目标是先得到可打开、可编译、可追溯的工程，再恢复指定功能。源码恢复、AssetBundle 提取和画面还原是三个相关但不同的任务：有 Prefab 不表示有工程；有工程不表示运行服务齐全；能够显示模型不表示恢复原游戏画面。

本文落实 [模块入口](../README_Tech_UnityCaptureReconstructionRules.md) 的 `UCR-EVD-01`、`UCR-AST-01`、`UCR-AST-02`、`UCR-ISO-01` 与 `UCR-VAL-02`，不新增同义规则。

## 2. 前提与依赖

先取得授权工作目录、预期功能、原始备份、目标平台以及可用编辑器。将“本次只需离线展示”和“恢复完整客户端”分开列验收范围，避免展示功能被登录、下载、CI 或移动端 SDK 阻断。

| 输入 | 建议记录 | 用途 |
| --- | --- | --- |
| 目录清单 | 工程根、资源备份、导出配置、平台包、工具、历史副本 | 防止在同名空目录或资源备份目录修工程 |
| 版本 | 编辑器版本及 revision、原定制引擎说明、包来源与锁文件 | 区分官方 API、包 API 和引擎私有扩展 |
| 原始资产 | 路径、GUID/fileID、大小、哈希、来源 | 保持引用身份，发现同名不同物 |
| 日志 | 编译批次、实际 Editor、工作目录、平台、完整日志 | 识别首个根因，避免依据截断截图修复 |
| 回退基线 | 本次拟改文件、原内容、meta、全局设置 | 支持定点回退，不覆盖他人修改 |

大型工程可先以文件索引和引用审计缩小范围；暂时不启动会自动改写全工程的升级、材质转换或重新导入。

## 3. 实现或排查步骤

### 3.1 先确定真正的工程根

检查同一目录下的 `Assets/`、`Packages/`、`ProjectSettings/`，再读 `ProjectVersion.txt`、manifest、包锁文件和本地包目录。缺少某一目录时先找历史副本；补骨架是有来源恢复或明确的新建工程，不能把猜出的设置写成原始配置。

建立“输入目录 → 作用 → 是否直接导入”的地图：

| 目录类别 | 处理方式 | 常见误判 |
| --- | --- | --- |
| 原工程 | 保留完整 Assets/Packages/ProjectSettings 与 meta | 只拿 Assets，丢失管线、层级和插件配置 |
| 美术备份 | 作为候选来源，按 GUID 和依赖恢复 | 将整棵备份树塞入 Assets，出现重复 GUID |
| 协议/表格导出 | 找实际生成的二进制表与脚本表 | 只看 Excel 源文件，忽略运行代码要读生成物 |
| 平台 AssetBundle | 先识别容器和资产映射 | 文件后缀或目录名直接当成格式证明 |
| Library/Temp | 视为可重建缓存，按需取诊断数据 | 把缓存当唯一源码或人工替换编译输出 |
| DCC/音频/CI 工程 | 判断是否属于当前功能依赖 | 缺作者工程就断言所有模型或声音不可恢复 |

编辑器安装版本与原定制引擎兼容性分开记录。同版本官方编辑器可能仍缺原厂修改的原生类型和内部 API。

### 3.2 保住定制包，再处理编译错误

本地包的 `package.json` 版本只能作为标签，不能证明其内容等同官方同版本。优先核对源码差异、manifest 的 `file:` 引用、包依赖和 Shader include。不要先升级整套 URP、ShaderGraph、TMP、渲染插件来消除旧 API 报错。

按以下顺序归类当前编译批次：

| 错误类别 | 查证入口 | 候选处理 |
| --- | --- | --- |
| 名称/命名空间缺失 | 定义搜索、程序集引用、asmdef、平台导入条件 | 补正确依赖或限制具体功能入口 |
| 同名 API 参数不符 | 当前包源码、目标 Unity 程序集元数据 | 写有边界的适配器，不按新版文档盲改 |
| DLL 强引用版本冲突 | AssemblyVersion、PublicKeyToken、依赖链 | 选择实际匹配的 DLL 组合 |
| 原生私有类型缺失 | 定制引擎/插件来源、调用覆盖范围 | 恢复匹配运行时，或明确降级该能力 |
| 序列化递归/缺脚本 | YAML、脚本 meta、对象图、引用数量 | 先确定数据迁移成本，再改类型结构 |
| 编辑器工具错误 | 运行时代码是否依赖、是否写资产 | 收窄到工具能力；显式动作缺依赖时失败 |

处理顺序通常是程序集/包 → 核心类型 → API 适配 → 可选能力 → 序列化与运行验证。持续按“最新完整批次”的根因重算错误集合，避免逐条修复由同一缺包衍生的数百条错误。

### 3.3 用能力边界降级，保留资产身份

能力隔离的目标是让不依赖该功能的工作可继续，同时让调用者知道功能不可用。可选原生服务、网络更新或 CI 构建入口适合按能力切分；序列化模型及资源身份通常不适合整体删除。

可迁移的设计：

1. 编译条件控制原实现是否参与编译。
2. 公开能力查询供 C#、脚本层与 UI 使用。
3. 缺能力的查询返回明确不可用；显式构建/导出请求在写入之前失败。
4. 不发成功回调、不生成假成功文件、不永久重试。
5. 保留本地资源、语言与基础系统的独立初始化。
6. 记录恢复该能力需要的包、引擎和运行条件；逐项启用后重新验证。

避免“定义一个同名空类便算恢复原生功能”。这可能让调用通过，却掩盖流送、碰撞、渲染或生命周期语义缺失。关闭整个 Editor 程序集也可能令场景、Prefab 和配置资产大量丢脚本。

### 3.4 把 DLL 当契约，而不是可互换文件

NuGet 包版本、DLL 文件版本、AssemblyVersion 是不同维度。匹配时检查实际引用者要求的程序集身份、目标框架与 API，并保留来源及许可证。

定制序列化库还可能附带 Unity 向量、集合等转换器。替换为更新的官方库即使编译通过，也可能改变配置格式和默认行为。此时可选择隔离要求新版本的可选服务，而不是牺牲核心序列化链。

若用目标编辑器自带编译器做离线编译，沿用实际响应文件、引用和 define，并写独立输出目录。其结果只覆盖编译契约，不能人工覆盖 `Library/ScriptAssemblies` 后宣称 Unity 导入成功。

### 3.5 建立多种依赖图

仅扫描 YAML GUID 不够。建议分别记录：

| 依赖图 | 边的含义 | 常见遗漏 |
| --- | --- | --- |
| GUID/fileID | 资产、子资产与脚本引用 | GUID 存在但子对象错误；重复 GUID |
| 脚本字符串路径 | Lua/C# 动态加载名称 | 资源改名、大小写不一致 |
| 配置表 | item/skin/paint 等 ID 映射 | 缺二进制生成表，不是缺 Prefab |
| Bundle 映射 | 逻辑资源名 → 路径/包/清晰度 | 同名不同变体或平台 |
| 运行时生成 | Shader/材质 → 动态纹理/缓存 | 把运行生成的空槽误判为丢贴图 |
| 场景运行状态 | 层、灯组、相机、全局量、质量等级 | 静态资源齐全但初始化链未执行 |

GUID 索引先覆盖 Assets 和本地 Packages，记录冲突而非让字典后值覆盖前值。恢复缺失引用时进一步检查 fileID、类型、依赖闭包和实际使用路径。未解析总数可用于分流，但不是视觉错误总数。

资源候选从原工程、历史副本、备份、生成目录逐层查找。只找到一个 Controller 而其 Motion/Avatar 仍缺失时，不把该 Controller 复制进去就宣称动画恢复。

### 3.6 让修复脚本可以安全重复运行

推荐以“计划 → 冲突检查 → 写入 → 清单 → 目标宿主验证”组织恢复：

- 目标不存在：按来源复制，保存对应 meta 或声明新建身份。
- 目标与源哈希相同：跳过，仍记录来源。
- 目标存在且哈希不同：报告冲突；人工确定来源后再处理。
- 全局设置：只补明确缺口，保留其他字段与现有用户配置。
- 层级配置：按数字槽位核对；名字相似不代表位掩码等价。
- 回退：核对当前文件是否仍等于本任务产物，再恢复原文件。

单纯文件复制可以幂等，语义仍可能错误：比如同名贴图来自另一版本，或一份配置引用未恢复的资产。因此清单同时保留版本、身份和依赖验证。

### 3.7 从解包失败的位置决定下一步

| 首个失败阶段 | 优先检查 | 此时尚不能证明 |
| --- | --- | --- |
| 文件/归档头不可读 | magic、长度、分片完整性、包装/偏移、读取 API、版本 | 贴图压缩格式不受支持 |
| 压缩块解析失败 | 压缩类型、块表、工具版本、源文件哈希 | 具体模型或材质坏了 |
| 对象反序列化失败 | Unity 版本、type tree、类布局、外部依赖 | 全包没有可用资源 |
| 纹理/网格解码失败 | 格式、平台 swizzle、mip/face、解码器 | 容器读取本身失败 |
| 导入正常但画面错误 | importer、颜色域、通道、Shader、运行绑定 | 原始数据一定损坏 |

先保留原包及日志，再选择原生加载或支持该格式的解析器。遇到私有包装时从证据开始识别；不要因扩展名是 `.ab` 就假设标准 UnityFS，也不要根据平台目录名跳到贴图解码结论。工具选择见 [工具、自动化与证据参考](unity-recovery-tooling-and-evidence.md)。

## 4. 风险与不适用边界

本文不保证第三方候选包等同原修订版，也不保证官方编辑器可恢复定制原生引擎功能。资产可导入与构建可发布分别验证；Editor 专用加载器不能自动迁移到 Player。

大范围重建 GUID、删除脚本、全量材质转换、升级包和序列化字段迁移会放大风险。对递归序列化或丢脚本问题，保留原对象图比“日志消失”更有价值。

## 5. 验证与回退

| 阶段 | 通过证据 | 不能替代的后续工作 |
| --- | --- | --- |
| 结构 | 版本、manifest、包路径、基础设置可解析 | Unity 导入 |
| 编译 | 当前目标完整编译批次及错误/警告统计 | 资源引用、原生插件 |
| 依赖 | GUID/fileID、动态路径、配置与生成输入闭包 | 运行状态与 GPU |
| 功能 | 指定入口实际打开、加载、切换和异常路径 | 全客户端或全目录验收 |
| 渲染 | 有图形设备的实际帧和分层对照 | 与原游戏一致性 |
| 交付 | 清单、来源、能力缺口、回退基线、复现入口 | 未测试平台与长期运行 |

恢复单功能时，交付说明明确“哪个入口可用、哪些功能停用、如何验证、哪些结论来自历史日志”。回退保留来源文件和证据目录，只撤销已确认属于本次的修改。
