# Unity 编辑态预览、自由相机与渲染状态恢复参考

> 类型：REFERENCE；适用范围：自定义渲染链的编辑态 Game 预览、Scene 自由视角与多相机调试；使用前提：以目标项目代码、资产、包版本和图形 API 重新验证。

## 1. 适用场景

本文用于解决“Play 可见而打开场景黑屏”“Scene 与 Game 走不同着色路径”“相机一转反射或阴影脱离”“打开第二视口影响第一视口”等问题。目标是让真实编辑器相机消费同一套实时几何、材质、光影及后处理，并保留导航与编辑能力。

本文提供实现模式与排错方法，不新增规范性规则。输入证据遵循 `UCR-EVD-01/02`，共享状态遵循 `UCR-ISO-01`，验收遵循 `UCR-VAL-01/02/03`，定义见[模块入口](../README_Tech_UnityCaptureReconstructionRules.md)。

项目具体版本、类与字段、菜单、布局偏移、场景和已完成验证见[龙之剑项目 Profile](../Profiles/DragonSwordAwakening/character-rendering-reconstruction.md) 的 DSA-08、DSA-09。源码旁的功能 README 继续负责使用方式与当前维护记录；迁移时重新建立目标项目 Profile。

### 1.1 先定义“一致”的层次

| 一致目标 | 可操作的定义 | 不由该目标自动保证 |
| --- | --- | --- |
| 渲染路径一致 | 当前相机执行相同几何、光影、透明、时域和后处理语义 | 任意窗口逐像素相同 |
| 同机位一致 | 固定姿态、时间、尺寸、镜像、抖动及历史后比较输出 | 转到未覆盖角度仍等价于原游戏 |
| 编辑行为一致 | 旋转、缩放、平移、选择与工具绘制使用正确相机和深度 | 离屏渲染通过即 GUI 交互通过 |
| 状态隔离 | Scene 渲染及关闭后，Game 输入与输出按契约保持 | 未测试的其他相机也已通过 |

自由视角会改变观察方向、透视、屏幕空间遮挡及历史，因此画面变化本身不构成失败。先固定上述定义，再决定比较对象和验收阈值。

## 2. 前提与依赖

开始前整理以下输入，避免在相机与着色都未知时同时调参。

- 目标 Unity、渲染管线包、图形 API、活动场景及实际 Renderer；检查包解析结果与工程配置是否相符。
- 唯一可识别的源 Game 相机、专用配置、运行时资源创建入口，以及哪些状态属于场景、相机或整工程。
- 原 GPU 事件的 View 元数据、矩阵约定、资源生产与消费顺序；场景真实模型、骨架和动画输入。
- 可恢复的原 Graphics、Quality、相机与 Renderer 状态，以及任务可写目录和代码/资产基线。
- 固定输入对照、阶段回读工具、实际 GPU Worker，以及可保留日志、图片和最终哈希的报告目录。

Shader 与 Feature 的一般组织见[Shader 开发模块](../../../ShaderDevelopment/README_Tech_URPShaderDevelopmentRules.md)；原渲染链恢复见[UE 渲染管线移植](unreal-render-pipeline-porting.md)。本参考从已能执行的渲染链开始，不替代完整解包与还原。

## 3. 实现或排查步骤

### 3.1 从用户真实入口定位首个失败

按“打开场景 → 默认 Game 预览 → Play → 退出 Play → Scene 导航 → 切场景 → 域重载”记录入口。显式设置管线的截图工具只能证明该工具路径；它可能绕开默认预览缺陷。

按首次错误与首次偏离的阶段排查：先检查前置资源创建日志，再定位抛错 Draw 的真实参数，最后查颜色链中最早错误的输出。最终黑屏可能只是更早的材质创建失败或管线未接管的结果。

| 现象 | 优先核查 | 容易误判的做法 |
| --- | --- | --- |
| 资源文件存在却空材质绘制 | 序列化引用、导入状态、名称查找、创建失败后的残留状态 | 直接认定文件丢失 |
| Play 正常、编辑态黑屏 | 默认预览是否触发管线接管与资源初始化 | 只补 Play 测试 |
| Scene 颜色与 Game 不同 | Scene 是否进入专用 Feature、组件与 View 改写路径 | 先重调材质或曝光 |
| 转动后光影漂移 | 顶点、片元、阴影接收者是否使用同一世界/相机约定 | 只修改顶点投影 |
| 第二视口污染第一视口 | MPB、纹理、运动矢量、历史与粒子状态的所有权 | 共享一个可变 Pass 实例 |

### 3.2 将资源初始化设计为可恢复事务

一组资源的“准备完成”由整个依赖集合决定，不由其中一个非空对象决定。材质对象有效、纹理对象有效、GPU 存储已创建分别检查；部分成功不能成为下一次提前返回的理由。

必需 Shader 可通过持久化资产引用表达依赖，并在生成配置时赋值。文件存在、成功导入、按名称查找成功是三个事实；未记录当时查找环境时，不补造查找失败的唯一根因。

以下为状态机伪代码，不是可直接运行的 Unity 实现：

```text
检查依赖引用与材质状态
若依赖缺失：清理本轮部分创建结果，报告来源，保留可重试状态
检查整组纹理对象与 GPU 存储
若目标失效：释放本状态拥有的目标，按契约重建，重置相关历史
仅在所有必需资源就绪后允许提交绘制
异常时清理本轮创建结果；下一次初始化仍能从一致状态开始
```

在未保存的测试配置副本中注入缺失引用、销毁运行时材质、释放纹理 GPU 存储，再恢复输入。比较恢复前后固定输入的阶段输出，确认画面及反射真的回来；只跳过空材质 Draw 只能避免异常。

### 3.3 用作用域管理编辑态管线所有权

接管条件可以限定为活动正式场景、唯一合法源相机、完整专用配置和匹配管线。Prefab 编辑、无源相机、多个候选或配置失效时，不猜测应该接管哪个来源。

接管前保存当前 Graphics、Quality 覆盖及必要蒙皮设置；临时预览期间记录“原值、自己安装的值、当前所有者”。清理时恢复自己仍拥有的状态，避免覆盖用户或另一工具之后主动设置的新值。

保存、场景切换、禁用、Play 过渡、域重载与退出都需要对应的归还路径。保存期间尤其关注临时预览值是否会被写入持久工程配置；临时相机组件和资源也与正式场景资产区分。

播放过渡可用显式状态机锁定所有权，待进入稳定编辑态后延迟重新判断。回归等待覆盖真实检查节流周期与宿主状态稳定条件；几个无时间约束的 update 不代表延迟逻辑已经运行。

不要根据一次回归的现象推定唯一内部回调次序。保留实际观察到的状态、时间和恢复结果，对未抓取的内部顺序标为未知。

### 3.4 把真实 Scene 相机接入专用渲染链

先确认差异是否来自 Scene 相机缺少 Game 专用配置而走了其他路径。对符合条件的真实编辑器相机建立临时绑定，复用源配置引用，并为每个相机分配其自己的渲染状态。

相机矩阵只在当前渲染作用域内安装。快照包含 projection、无抖动 projection、culling、aspect 及自动投影状态；结束后恢复。异常中断、编辑器更新与场景 GUI 回调可承担兜底恢复，但不持续覆盖用户导航。

仅把矩阵数值写回原值可能仍保留“手动矩阵”模式，造成旋转或缩放之后投影不再更新。目标版本中恢复自动生成模式与恢复矩阵值分别验证。

自由视角需要当前几何与当前相机真正重渲染。把 Game 结果作为 Scene 背景只能提供固定预览，不能证明自由观察、深度选择和遮挡已恢复。

### 3.5 先冻结 View 布局与坐标契约

按 Shader 元数据识别 View 常量缓冲的语义、成员偏移与矩阵读法；缓冲大小可作辅助线索，不能替代语义识别，也不假设所有 Shader 占用同一个槽位。

区分逻辑字节长度与向量对齐后的传输长度。只给未使用尾部补零，保持有效字段字节和数组索引稳定；校验范围覆盖所有实际使用的 Shader 变体。

转换表至少明确以下约定：

| 契约 | 核查内容 |
| --- | --- |
| 线性代数 | 行/列向量、矩阵存储、乘法顺序、转置与逆矩阵 |
| 世界坐标 | 单位、轴交换、手性、负缩放、固定世界原点与相对原点 |
| 投影 | 透视/正交、镜像、GPU 深度范围、反向 Z、离轴项 |
| 屏幕 | 顶/底原点、RT 与窗口尺寸、像素中心、viewport 与动态缩放 |
| 时间 | 当前 raster jitter、无 jitter 投影、前帧变换、历史重置 |

顶点用当前相机、片元重建仍用抓帧 View，会产生看似材质或灯光问题的混合坐标错误。把 view/projection、inverse、screen/world、相机位置、尺寸、设备深度和 FOV 作为一组契约更新。

材质、曝光、氛围等非相机参数继续保留其原始来源。不要为适配视角把整个缓冲换成另一个来源，从而悄悄改写光照或后处理。

### 3.6 分开处理当前帧、无抖动与前帧矩阵

当前 raster projection 用于实际光栅位置；无抖动 projection 用于稳定重建或编辑器工具；前帧 View 用于运动与时间历史。三者含义不同，初始化前帧等于当前帧只是一个历史启动策略。

透视与正交的抖动项位于不同矩阵位置，直接复制同一“去 jitter”公式可能只在一种投影下正确。用世界点投影及深度重建的独立代数样本分别检查。

若原阴影生产者的投影、覆盖范围与 caster 集合仍适用于新视角，可以保留光源世界变换，仅替换接收者从当前屏幕到世界的映射。相机相关的级联、随视口拟合的阴影范围或视角相关 caster 剔除则还需重验生产者，并更新对应投影、绘制集合及采样选择；接收者正确不代表 shadow map 覆盖完整。反射若有独立 translated origin，重建光源位置时按该来源重新基准化；齐次方向量不受平移影响。

### 3.7 隔离 MPB、相机历史与共享模拟

共享 Renderer 的 MaterialPropertyBlock 可能含其他系统数据。读取并保存完整原块，在副本上改写当前相机字段，在相关绘制完成提交后通过 `finally` 恢复，避免只恢复自己知道的属性。

可采用“借用配置、拥有状态”的模型：源材质与静态配置只读复用；GBuffer、反射、运动矢量、时间历史及可变常量由每个相机拥有。清理时区分借用资源与自建资源。

多个视口通常共享同一世界模拟时间与粒子状态，再按各自相机生成 billboard 等视角相关几何。每个视口各启动一套随机模拟，会让同一时间的 Scene/Game 无法比较。

关闭视口、源对象失效、域重载或配置切换时回收对应状态；同时检查相机键是否继续保留失效对象。单相机稳定不代表长期打开关闭多个窗口不会泄漏。

### 3.8 分别追踪反射生产者与消费者

镜像平面决定反射相机，显示反射的几何却可能是朝向相机的卡片。先追踪反射 RT、UV、消费者 Shader 和真实顶点输入，再判断它是世界平面投影、屏幕采样还是普通 UV 卡片。

反射 RT 的宽高比可能独立于主窗口。生产者保留水平 FOV、纵向 FOV 或正交范围中的哪一项，会改变消费者的缩放关系；从两端投影共同推导映射，不只复制主相机宽高比。

“保持原卡片 NDC 不变”不是普适正确目标。主窗口转竖屏时模型跟随新投影而卡片仍停在源位置，就可能出现脚底与倒影分离；数值测试若验证同一个错误假设，也会误报通过。

独立预期可使用当前主图与反射投影关系、已知接触点和源几何。测试横屏、竖屏、方形、超宽、透视、正交与镜像；检查脚底接合、倒影方向和纹理覆盖边界，而不只检查有限像素。

固定展示卡片可能无法覆盖任意自由视角的完整反射轮廓。区分映射错误、卡片作者范围和场景本来缺失的几何；不要用“原布景有边界”解释真实的投影错位。

### 3.9 让 Scene 深度与最终颜色使用一致变换

最终颜色正确不能证明后续编辑器工具拿到正确深度。颜色的图像 Y 变换、去 jitter 与输出尺寸换算，也需要应用到深度写入或复制路径。

Shader 全局纹理名称不一定等于可绑定的真实渲染目标标识。优先获取该帧管线实际分配的 handle；读取管线拥有的 handle 不代表取得释放权。

若适配依赖包内非公开成员，将该依赖留在项目 Profile，限定版本与失效处理。字段缺失时跳过目标可以避免异常，但结论相应降为“深度路径未确认”，不能以无错误替代正确回写。

自定义 Pass 结束后，后续 Gizmo、Handles 或选择绘制可能仍消费相机全局矩阵。恢复正向、逆向与无抖动投影，并验证目标版本的实际调用时序。

离屏真实 Scene 相机渲染能检验颜色、资源和部分恢复断言；它未驱动 GUI 拾取、工具手柄、鼠标导航时，就没有覆盖那些交互行为。

### 3.10 按证据层选择工具

| 工具或方法 | 主要回答的问题 | 不能单独证明 |
| --- | --- | --- |
| 日志与源码搜索 | 首个资源失败、实际调用参数、状态所有者 | GPU 输出与视觉正确 |
| Shader 元数据解析 | 常量语义、布局、槽位和实际使用字段 | 当前 C# 写入一定正确 |
| 独立矩阵脚本 | 轴/单位、投影/重建、反射映射的代数关系 | Unity 与 GPU 已执行该算法 |
| 离线全工程编译 | 当前源码与目标引用的 API 兼容性 | 宿主导入、渲染与 Play 正常 |
| 实际 GPU Worker | 真实相机、阶段回读、历史、恢复及播放 | 未驱动的 GUI 行为 |
| 分阶段读回与差异图 | 首个偏离阶段及空间分布 | 非黑、finite 即视觉完整 |
| 独立图片复核 | 网格/材质完整性、反射接触、曝光与构图 | 连续动画与原游戏全视角等价 |
| 哈希清单 | 源码、报告和图片的具体字节身份 | 内容本身达到效果要求 |

离线编译方法见[Unity Editor 脚本离线编译验证](../../../ToolDevelopment/references/unity-editor-script-offline-compile-verification.md)，后台执行与交付见[独立 Worker 与验证](isolated-unity-worker-and-delivery-validation.md)。

日志采集除 Error/Exception/Assert 外，还可精确纳入已证实会破坏渲染的 Warning 模式。不要因为某类 Warning 没进错误数组，就把依赖失效当作通过；也不把一个专项过滤器描述为“所有 Warning 为零”。

## 4. 风险与不适用边界

- 同一路径仍可能保留原捕获的镜像、源宽高比、随机与历史差异；自由导航友好的投影不一定与原 Game 显示方向相同。
- 本文的反射适配方法以证据确定 producer/consumer 关系；项目某个卡片缩放公式、缓冲大小或字节偏移不是跨项目常量。
- 编辑器相机与预览资源的内部实现会随 Unity/管线版本变化；升级后重新检查分配、自动矩阵、深度复制及工具绘制时序。
- 少量静态图不能覆盖动画连续性、透明排序、全部遮挡或多 Scene 窗口同时交互。受测角度与角色集合单独记录。
- 原展示场景可能只有相机前方布景；侧后方看到边缘或空区需要根据源几何判断，不能自动补全并宣称来自原游戏。
- 不干扰鼠标的 Worker 验证适合多数回归，但不能凭它把未操作过的 GUI 行为记为已完成。
- 主编辑器失去响应或资源压力过大时，优先保存日志与检查点；旧备份不代表全部未保存状态，重启风险与普通后台检查分开处理。

## 5. 验证与回退

### 5.1 按层记录验证命题

| 层级 | 最小检查 | 报告边界 |
| --- | --- | --- |
| 资源与布局 | 引用完整、逻辑/传输长度、矩阵约定及失效重建 | 不替代实际画面 |
| 独立代数 | 源数据推导的投影、重建、阴影和反射预期 | 不执行生产实现的结果单独标明 |
| 真实 GPU | 每个关键阶段、颜色/深度、有限性、历史与日志 | 结构通过与视觉通过分开 |
| 视觉复核 | 角色与配件、反射接触、曝光、背景边界和裁切 | 离屏部分与未受测角度不外推 |
| 生命周期 | 默认打开、Play 过渡、保存、切场景、域重载与清理 | 显式调用管理器不能替代自动入口 |
| 编辑交互 | 实际旋转缩放、选择、Handles/Gizmo、多窗口 | 无 GUI 操作时保留未验证标记 |
| 工程健康 | 编译、Shader 诊断、场景引用、配置与原内容保护 | 不替代渲染一致性 |

### 5.2 固定输入的相机交错验证

执行 `Game → Scene → Game`，固定动画时间、世界状态、相机输入和历史策略。比较前后 Game 输出以及配置、MPB、临时组件与相机矩阵；这样能直接发现 Scene 污染共享状态。

同机位 Scene/Game 对比明确分辨率、颜色域、镜像校正、抖动相位、历史帧数和区域定义。矩形区域不要命名成分割 mask；记录 MAE 等指标不自动等于已满足事先未设定的阈值。

再覆盖 Scene 关闭/重开、源场景失效、透视/正交切换与不同 aspect。多窗口交错渲染和真实多窗口 GUI 交互分开统计，避免用一种覆盖替代另一种。

### 5.3 保留失败样本与最终产物身份

测试输出仅标记 finite、非黑时，报告名称与结论保持在结构层。出现视觉失败后保留失败图及其当时通过的报告，用于修订验收目标，避免旧指标继续掩盖同类问题。

源码变化后，注明哪些验证早于最后改动、哪些覆盖最终代码。以前通过的长时间 Play 报告不自动升级为最终 Scene 专项修改后的重跑结果。

报告、截图、视觉复核和文档定版后再计算最终清单。重写同一路径图像会改变其身份，原 QA 只能证明原哈希对应内容；保留旧结果时使用独立前缀或归档目录。

### 5.4 缩小回退范围

先关闭本功能入口并归还临时状态，再回退本任务拥有的代码与资产。核对原管线、质量设置、源相机、场景序列化及借用资源仍完整；不因共享目录发生变化而覆盖其他任务修改。

若只确认颜色路径而尚未确认深度或 GUI，将限制写入项目 Profile 与交付说明。补测按未确认命题执行，已通过且未受后续改动影响的测试无需机械重复。

更广的图像比较、GPU 输入和故障定位方法见[RenderDoc 验证与故障排查](renderdoc-validation-and-troubleshooting.md)。
