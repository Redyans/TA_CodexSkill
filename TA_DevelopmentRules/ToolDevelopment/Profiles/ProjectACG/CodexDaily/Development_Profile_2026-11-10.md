## 1. RT 颜色诊断的定位与操作

**项目事实/现象**：用户报告 `UIBlurBackground_Snapshot` 发灰，并在消息 12 明确是 Inspector 点击 RT 后的预览。由此排除“先从 UI 遮罩解释”的方向；Snapshot 已经过模糊，还需与模糊前图比较。来源：S2 消息 7–21。

**根因状态**：当时助手报告 Unity 2022.3 的 `RenderTextureDescriptor(width,height,RenderTextureFormat.Default,0)` 默认走非 sRGB/Linear，项目未覆盖；怀疑截图数据和声明域不匹配，再被预览编码一次。尚未读到真实结算截图的同帧对照，根因未确认。消息中给出的 0.2→约 0.485、0.5→约 0.735 是“若已编码值被当成 Linear”的条件示例，不是实际结算像素。

**项目约束或修正**：加入支持编辑态与编辑器 Play Mode 的诊断窗口，并接入现有调参器。使用流程：

1. 在 Play Mode 运行游戏并打开结算。
2. 打开 `TEngine → UI → 背景模糊调参器`。
3. 点击“检查 RT 原始像素 / sRGB 与 Linear 对照”。
4. 选择“模糊前备份”或“模糊后结果”，点击“读取 / 刷新像素”。
5. 比较 A（按已编码 sRGB 显示）与 B（按 Linear 转为 sRGB）；可点击取点、导出对照 PNG。
6. 也可从 `TEngine → UI → RT颜色诊断` 直接检查选中的 RT。后续增加直接图片预览和“Snapshot 当前输出”选项。

若 A 接近原画面、B 接近发灰预览，只更支持重复转换假设，仍要与同帧已知输入确认。具体诊断脚本文件名、回读 API 和完整实现代码未出现在当日采用消息中，不补写。

**验证证据**：17:00 报告编译与 36 项 D3D11 GPU 检查通过，覆盖 RGBA/BGRA 原始字节回读、两种解释、PNG 导出，源 RT 未改。其验证对象是诊断工具，不是原问题的结算画面。

**未验证项/回退**：当前结算 RT 根因仍待确认；工具只用于编辑器，未接入打包游戏。使用前还需确认所选 RT 有效，避免将无数据输入误解成工具失败；这属于使用前提，不是已实现的错误处理保证。

## 2. 同帧原图输出、直接预览与误回退修复

**项目事实/现象**：用户希望直接看到拍摄 RT 的颜色，并让 Snapshot 输出不经过模糊的原图。稍后报告改动被误回退。来源：S2 消息 22–31。

**根因**：初始 UI 缺少直接图片观察及可切换原图输出；误回退后，来源检查发现调参器的“跳过模糊”开关和诊断入口丢失，但图片预览与诊断窗口仍存在。回退由哪次操作造成，消息没有证据。

**项目约束或修正**：

- 在调参器选择 `Settlement`，勾选“输出原始截图（跳过模糊）”。
- 把已保留的模糊前同一张截图写入 `UIBlurBackground_Snapshot`，避免重新拍摄混入场景变化。
- 取消勾选、切换实例或关闭调参器时，设计为恢复模糊输出。
- 诊断窗口直接展示所选 RT；选“Snapshot 当前输出”查看实际图像。
- 19:41 报告仅补回缺失入口与开关，底层窗口保留。

**验证证据**：开关和预览首次交付报告编译通过；恢复后再次报告编译通过。不是已在真实结算界面完成开关/关闭窗口/切换实例验收。

**未验证项/回退**：实际结算使用仍未测试，Domain Reload、异常和 Player 构建行为缺失。会话声明的恢复动作是待实景确认的实现行为，不写成自动化实测；关闭诊断开关可回到模糊输出，若失效应先核对备份与目标实例。

## 3. 半精度浮点支持与“黑图”误判纠正

**项目事实/现象**：用户要求 RT 使用截图所示 R16 格式，来源明确识别为四通道 `R16G16B16A16_SFloat`，不是单通道 R16。来源：S2 消息 32–40。

**根因/修改目的**：提高截图与滤波链的数值精度；不能把精度需求等同于发灰根因已经验证。

**项目约束或修正**：

1. 截图、原图备份、模糊缓存使用同一浮点格式，避免中间降回 8 位。
2. 诊断取点保留原始浮点 RGBA；A/B 预览与 PNG 仍用于 SDR 对照，0–1 外截断，不承担 HDR 精度验证。
3. 在 Inspector 中直接修改运行 RT 格式会重建纹理并丢失旧截图。交付操作是等编译完成后重新进入 Play Mode、重开结算，由代码重新截图。
4. 2560×1440 下每张约 28.1 MiB，是原 8 位 RGBA 两倍；该值不是整个模糊系统的总显存。

**验证证据**：
