# Unity 网格拆分、清理与撤销开发参考

> 类型：REFERENCE；适用范围：Unity Editor 中将一个渲染对象转换成多个对象，同时生成独立资产、可选移除源组件的工具；使用前提：按目标版本、Mesh 数据、Prefab 类型及消费者重新验证。
>
> 本文提供实现选择和排查方法，不新增与 CORE 平行的强制规则。规范来源是[工具开发模块](../README_Tech_TAToolDevelopmentRules.md)的 `TOOL-CMP-01`、`TOOL-ARC-01/02`、`TOOL-UI-01/02`、`TOOL-OPS-01/02/03`、`TOOL-VAL-01/02/03`。实际案例和测试材料见[子网格拆分工具 Profile](../Profiles/ProjectACG/submesh-splitter-cleanup-and-output.md)。

## 1. 适用场景

适合子网格拆分、按材质分件、Renderer 替换、模型代理生成，以及“先生成结果，再清理来源”的批处理工具。核心难点在于让内存对象、磁盘资产、场景层级、外部引用和撤销记录在成功、失败、取消时保持一致。

阅读顺序：先用第 2 节冻结行为，再按第 3 节实现；出现异常时查第 3.12 节；交付前使用第 5 节的验证矩阵和复用清单。只需要编辑导入预设时，优先读取[ModelImporter 与安全 Mesh 生成参考](model-importer-preset-and-safe-mesh-generation.md)；需要迁移完整组件和子树时，优先读取[Prefab 快照与事务恢复参考](prefab-module-snapshot-and-restore.md)。

## 2. 前提与依赖

### 2.1 把自然语言转换成可检查契约

| 用户表达 | 实现前澄清的含义 | 可检查结果 |
| --- | --- | --- |
| 拆分后清理原网格 | 删除哪些组件；是否保留容器、脚本、碰撞体和既有子节点；默认开关状态 | 原组件按配置保留或删除，其他内容完整 |
| 保存到原 Mesh 本地 | 指源 Mesh 对应资源目录，还是场景、Prefab 或最近一次目录；多来源是否分别输出 | 每个来源使用可追溯的输出目录 |
| 也可指定路径 | 只允许工程资产目录，还是另做外部导出；无效路径如何处理 | 选择器与执行层使用同一校验 |
| 在场景中显示 | 创建对象、绑定持久 Mesh、继承显示状态、选择定位、实际渲染分别验收 | 层级、组件、引用、状态和视觉证据分别成立 |
| 可以撤销 | 只恢复场景，还是连资产一起删除；Redo 是否仍能读取 Mesh | 一次 Undo/Redo 的边界明确且可复现 |
| 支持取消 | 当前项回滚，还是整批回滚；已完成结果是否保留 | 取消点明确，没有当前项半成品 |

“干净 GameObject”更适合定义为“移除本工具负责的渲染组件后保留容器”。把整个对象删除、删除所有组件或清空已有子节点，会把用户没有授权的内容也纳入转换。

新增破坏性开关可默认关闭，先展示本次范围、输出和清理影响，再按 `TOOL-OPS-01` 的既有确认流程执行。对已有工具，默认值、序列化字段、菜单、命名、路径优先级和写入时机都属于兼容契约；有意改变时记录迁移理由。

### 2.2 识别五类状态及其所有者

| 状态 | 常见对象 | 建议记录 | 结束时的处理 |
| --- | --- | --- | --- |
| 来源状态 | 原 Renderer、Transform、材质、骨骼、LOD 引用 | 来源身份和必要快照 | 成功后按开关清理；失败恢复 |
| 临时数据 | 顶点映射、提取的内存 Mesh | 是否已持久化、谁负责释放 | 未持久化对象在异常和取消时释放 |
| 新资产 | 独立 Mesh 文件及其元数据 | 仅本事务创建的路径 | 失败删除；成功按资产回滚契约保留 |
| 场景结果 | 子节点、组件、LOD 修改、Prefab overrides | 本项 Undo 分组和已创建对象 | 失败撤回本项；成功并入批次 Undo |
| 编辑器状态 | Selection、进度条、窗口状态、SceneView | 本次操作拥有的状态 | 在 `finally` 清理进度和收束分组 |

资产和场景使用不同的持久化机制。`Undo` 能恢复的场景操作，不自动等于磁盘文件已经安全回滚；调用 `CreateAsset` 也不表示原场景已经保存。

### 2.3 先确定 Mesh 数据契约

检查来源类型、拓扑、CPU 可读性、索引格式、材质槽与 SubMesh 对应、法线/切线/颜色、全部需要的 UV、骨骼权重、Bind Pose、BlendShape，以及真实 Shader 的额外顶点流要求。对不支持的数据给出范围，而不是笼统承诺“无损”。

工具代码位于 Editor-only 边界。读取已导入 Mesh 并生成外置资产，与直接改写 FBX 是两类任务；后者另见[FBX 源数据编辑器参考](fbx-source-asset-editor-development.md)，不因一个拆分按钮而默认扩展到源文件写回或全局导入 Hook。

## 3. 实现或排查步骤

### 3.1 先收集快照，再修改层级

推荐顺序为“收集来源 → 按对象身份去重 → 校验候选 → 执行”。父子同时选中时，同一 Renderer 可以被遍历多次；去重键适合使用 Renderer 身份，不能使用名称或 Mesh 身份。两个 Renderer 共享一个 Mesh 仍然是两个需要处理的场景实例。

把来源收集到固定列表之后再新增子节点，可避免边遍历边生成时把新结果重新当作输入。列表还便于进度统计、错误定位和确认范围。静态与蒙皮来源可以共享调度、路径和事务逻辑，但各自使用正确的结果组件；“能够混批拆分”并不推导出“能够混合合并”。

候选校验可分别报告：资产对象而非场景实例、缺少 Mesh、单 SubMesh、不支持的 Renderer、未读到完整数据、非法目录、当前处于 Play Mode。真正执行前再次校验关键引用，防止窗口绘制时的旧状态直接进入写入。

### 3.2 用顶点映射提取子网格

提取一个 SubMesh 的通用思路是：读取其索引 → 为引用到的旧顶点分配新索引 → 按同一映射复制每种顶点属性 → 写入独立 Mesh。概念示例如下，属于算法说明，不是可直接替代完整实现的代码：

```text
oldToNew = 旧顶点索引到新顶点索引的映射
newToOld = 新顶点索引到旧顶点索引的顺序表

遍历当前 SubMesh 的索引：
    旧索引尚无映射时，分配新索引并记录到 newToOld
    将映射后的索引追加到输出索引

对每个支持的顶点通道：
    按 newToOld 从源通道复制值
对每个 BlendShape 的每个 Frame：
    按 newToOld 复制位置、法线和切线 Delta
写入拓扑、索引、Bind Pose、Bounds 和名称
```

各通道共享同一映射；只重建顶点和三角形会丢失 UV、颜色或蒙皮信息。已有通道的维数也会影响语义，例如四维 UV 不能随意降为二维。没有来源法线/切线时是否重算、是否保留分裂顶点，都属于输出策略。

处理索引时同时检查 `MeshTopology`、`baseVertex` 和目标 API 的索引偏移语义，不能把所有输入都当作普通三角形。空 SubMesh 是可出现的数据，产品可以选择保留空槽、跳过并映射材质，或整项拒绝；先定义策略，再核对生成数量，不能默默删除来源后丢掉一部分。

输出索引格式按最终顶点数与目标平台能力选择，并在边界两侧验证。CPU 可读性失败时，先明确报告来源；如果确需临时改导入设置，使用已有的快照、恢复流程，不在此处偷偷永久开启全项目 Read/Write。

### 3.3 分别保持静态与蒙皮语义

| 项目 | 静态结果 | 蒙皮结果 |
| --- | --- | --- |
| 场景组件 | MeshFilter 与 MeshRenderer | SkinnedMeshRenderer |
| 网格引用 | 持久化 Mesh 的共享引用 | 持久化 Mesh 的共享引用 |
| 材质 | 来源对应 SubMesh 的材质 | 同左 |
| 坐标 | 新子节点局部单位变换，继承来源空间 | 同左，另核对骨架空间 |
| 专属数据 | 光照贴图、静态标志等 | bones、rootBone、Bind Pose、权重、quality、Bounds 等 |
| 形变 | 按数据契约保留 | 完整 Shape/Frame/Delta 与当前 Renderer 权重分别处理 |

若结果继续位于原对象下，`SetParent(sourceTransform, false)` 配合局部单位变换，可保持 Mesh 所在空间；不要在已经继承父变换后又烘焙一次世界矩阵。非均匀缩放、负缩放和骨骼动画仍需样本验证。

复制 Renderer 设置时建立显式清单：enabled、阴影、探针、probeAnchor、动态遮挡、motion vector、rendering layer、排序、lightmap index 与 scale/offset 等。使用共享材质引用，避免仅为了分配槽位触发材质实例化。缺失材质、多余材质槽和自定义 `MaterialPropertyBlock` 分别定义策略。

复制完整 Static Flags 比复制单个 `isStatic` 更准确，但保留光照贴图字段不代表拆分后烘焙语义自然成立。静态合批、遮挡、Lightmap 和项目自定义渲染数据需要在真实场景复核。

BlendShape 的“Mesh 中存在数据”和“Renderer 当前权重正确”是两件事。Bounds 同样影响形变后可见性：只按静态顶点重算可能导致动画伸展时被裁掉；可以保留来源形变范围，再通过实际极限姿态验证。

### 3.4 将输出目录和资产命名设计为独立策略

一种可迁移的目录决策顺序是：显式自定义目录 → 当前来源 Mesh 对应的可写资产目录 → 可追溯的 Prefab 目录 → 工具约定兜底目录。具体优先级由项目 Profile 固定。多来源默认输出时，可按每个来源独立解析，而不是只用第一个选择项。

| 输入位置 | 建议判定 | 处理选择 |
| --- | --- | --- |
| 工程资产根或其子目录 | 对象路径有效且确认为文件夹 | 允许作为资产输出 |
| 工程外文件夹 | 不属于 AssetDatabase 资产空间 | 拒绝，或进入另行设计的导出流程 |
| 包目录、只读位置 | 存在不等于可写 | 采用明确回退或给出错误 |
| 临时 Mesh、无资源路径 | 不能由 Mesh 找到磁盘目录 | 使用已定义的 Prefab/兜底策略 |
| 普通文件伪装为目录 | ObjectField 可能接收错误类型 | 执行前拒绝 |

UI 可用文件夹对象拖入与文件夹选择器，最终都转换成项目相对路径并进入同一校验。区分资产根目录与带分隔符的子目录前缀，避免把类似名称目录误判为合法；自定义开关打开但路径无效时，明确拒绝通常比静默回退更容易理解。

文件名只从预期名称生成，清理非法字符；通过唯一资产路径 API 避免覆盖旧资源。不要把对象名直接拼成可逃逸的磁盘路径。覆盖和唯一新增是不同产品行为，性能优化时也不能暗中互换。

### 3.5 先落盘并绑定结果，再清理来源

每个来源可采用以下提交顺序：

```text
校验来源和目录
→ 提取全部所需子 Mesh，并验证完整性
→ 为本项分配独立 Undo 分组
→ 逐份保存 Mesh，记录本项新资产路径，检查持久化
→ 创建全部场景子对象并绑定有效 Mesh
→ 替换支持范围内的引用
→ 按开关移除来源组件，并确认删除成功
→ 标记受影响场景 Dirty
→ 将本项结果加入批次成功列表，提交本项
```

来源清理放在末尾，能缩短“原对象已丢失、替代物未就绪”的窗口。节点创建失败且尚未进入 Undo 时，由创建函数释放自己创建的临时节点，随后交给事务处理其他状态。

调用 `CreateAsset` 后检查对象是否持久化，可发现部分没有表现为预期异常的失败。不过这不等于完整磁盘完整性验证，重新加载、保存重开仍是另一层证据。

`StartAssetEditing/StopAssetEditing` 适用于已确认可延迟导入的流程；如果本流程依赖即时导入、持久化检查及同轮引用绑定，可先选择同步创建保证正确性，再基于测量改造批处理。使用批编辑时仍按 `TOOL-OPS-02` 成对保护，避免在暂停导入期间依赖尚未完成的导入结果。

### 3.6 删除组件同时修复可控引用

“清理组件”实际是一次对象图转换。删除前检查：哪些组件依赖它、哪些序列化引用指向它、哪些动画轨道按路径或名称写入它。

对于支持范围内的 LODGroup，可遍历其 LOD 数组，将原 Renderer 的每个引用位置替换为全部新 Renderer，保留其余 LOD 参数。修改前记录 Undo，修改后记录 Prefab 实例属性变更。仅替换第一个 LOD 或只创建子节点，都可能使结果在某些距离消失。

对脚本字段、Timeline/Animator 绑定、自定义组件和外部 LODGroup，局部工具不宜假装可以自动完成全部重绑；提供明确边界，必要时做单独扫描、映射和用户确认。若要恢复任意组件或层级，引用现有快照方案，不在拆分窗口中临时发展另一套反射迁移框架。

组件移除可以先 Renderer、后其静态 MeshFilter。Unity 可能因依赖关系拒绝销毁而只写日志，因而“没有 C# exception”并不能证明成功。销毁后用 Unity 对象语义检查组件是否仍存在，若仍存在则让当前项失败并回滚；不要把删除依赖脚本当作自动补救。

Prefab 场景实例的添加、删除和属性修改属于 overrides；自动 Unpack 或 Apply 会扩大用户授权范围。普通 Prefab、Model Prefab、嵌套、Variant 和 Prefab Mode 分别验证，不从单一普通实例的测试推导全覆盖。

### 3.7 逐来源事务与整批事务的选择

| 策略 | 适用情形 | 代价和结果 |
| --- | --- | --- |
| 逐来源提交 | 来源彼此独立，希望批次允许局部成功 | 当前项回滚，已完成保留，报告部分成功 |
| 整批原子提交 | 多个来源共同构成不可分割产物 | 全部准备好后提交，失败撤回全部，资源占用更高 |
| 仅停止后续项 | 已完成步骤无法恢复或代价不可控 | 执行前说明已写入部分如何人工恢复 |

逐来源事务可记录 `createdAssetPaths`、新对象列表、本项 Undo group 和 `completed`。只有所有子步骤完成才设置提交标记。在 `finally` 中，未提交则撤回本项 Undo、删除本项新资产，并释放所有未持久化的临时 Mesh。

只删除“本事务拥有且确认新建”的资产，避免依据模糊文件名前缀清理。后续增强可单独报告 DeleteAsset 返回失败或回滚异常，避免把“已尝试回滚”写成“已确认完全恢复”。外层异常也与逐项异常分开处理，尤其是最终保存、刷新和结果展示失败。

取消放在安全检查点，例如开始某个 SubMesh 前。单次提取、资源创建或同步导入内部通常无法立即取消；进度文字应反映阶段。可用 `(已处理来源数 + 当前来源内完成比例) / 来源总数` 表示近似进度，但它不是精确时间预测。

### 3.8 把场景 Undo 和资产寿命分开设计

推荐先决定成功资产的所有权，再写 Undo。常见选择如下：

| 成功资产策略 | Undo 场景后 | Redo 场景时 | 适用边界 |
| --- | --- | --- | --- |
| 保留生成资产 | 资产仍在目录中 | 继续引用同一资产 | 需要说明资产人工清理方式 |
| 自定义资产事务 | 同步移除或恢复资产 | 同步重建同一身份或重新绑定 | 实现复杂，需要专门测试 GUID、重导入与历史引用 |
| 不提供场景 Undo | 靠版本控制/备份恢复 | 没有 Redo 承诺 | 适用于独立资产批处理，界面明确说明 |

保留成功资产可降低 Redo 出现 Missing Mesh 的风险，但会留下已撤销场景使用过的资产。失败项的补偿删除，与成功后用户主动 Undo，是两个不同动作，不能套用同一清理分支。

下面是“场景批次最终收束”的顺序示意，仅展示公开 API 的位置；其中注释代表由具体工具实现的步骤，不是完整可运行工具：

```csharp
Undo.IncrementCurrentGroup();
int batchGroup = Undo.GetCurrentGroup();
Undo.SetCurrentGroupName(operationName);
try
{
    // 逐来源执行；每项拥有自己的 Undo group 和新资产清单。
    // 失败项只 RevertAllDownToGroup 自己的 group。
    AssetDatabase.SaveAssets();
    AssetDatabase.Refresh();
    // 更新 Selection、Ping、SceneView 与 Hierarchy 结果展示。
}
finally
{
    Undo.FlushUndoRecordObjects();
    Undo.CollapseUndoOperations(batchGroup);
    Undo.IncrementCurrentGroup();
    EditorUtility.ClearProgressBar();
}
```

关键在于最终 Collapse 覆盖本次批处理、资产刷新与结果展示产生的同步 Undo 记录，而不是仅包住主体循环。若把 Flush/Collapse/Increment 放在循环结束后、刷新和选择之前，最后的一次 Undo 可能只撤掉后续记录，未恢复用户预期的来源组件。

该顺序仍需要在目标版本验证。异步回调若稍后继续改场景，不能仅靠同步 `finally` 自动纳入已结束批次；应重新设计完成边界。生产逻辑使用公开 Undo API；内部历史记录反射只适合临时诊断，不作为兼容承诺。

### 3.9 将“结果可见”拆成多个证据层

1. 层级：对象创建在正确场景和父节点下，没有生成到资产预览或错误 Stage。
2. 引用：Renderer/MeshFilter 引用有效持久 Mesh，材质槽符合对应关系。
3. 状态：局部变换、activeSelf/activeInHierarchy、Renderer.enabled、layer 和相机剔除相容。
4. 关联：LOD 当前层引用新 Renderer，骨骼与 Bounds 能覆盖真实姿态。
5. 反馈：选中新结果、定位对象、可选聚焦 SceneView，并刷新层级。
6. 图像：在目标场景、目标相机与实际材质下观察几何、光照、LOD 和形变。

自动选中或 `FrameSelected` 只改善定位，不会修复被禁用的 Renderer、关闭的父节点、错误 Layer、空材质、裁剪或 Shader 问题。为了“让它显示”而强制激活所有父节点，也会破坏原场景行为。没有活动 SceneView 时可跳过聚焦，结果生成仍可成功。

场景修改后标记 Dirty，让用户决定保存；自动保存当前场景会扩大操作副作用。

### 3.10 用工具链逐层缩小问题

| 工具/方式 | 适合回答的问题 | 不能代替的证据 |
| --- | --- | --- |
| `rg`、Git diff、状态检查 | 入口、字段、消费者、修改范围 | Unity 的对象和资产行为 |
| 文件哈希 | 运行测试的源码是否对应当前版本 | 行为本身是否正确 |
| C# 编译器与响应文件 | 语法、公开 API、选定程序集引用 | Undo、Prefab、序列化和可见性 |
| 最小 Unity 工程 | 降低工程噪声，执行资产与场景断言 | 生产项目程序集、真实资产和渲染 |
| Unity 批处理日志与结果文件 | 是否运行、断言是否完成、退出状态 | 真实窗口交互和 GPU 图像 |
| 正式场景人工复验 | 材质、动画、光照、LOD、操作体验 | 全数据集和全部异常注入 |
| UTF-8 严格读取与文档链接检查 | 知识库内容完整、导航可用 | 工具功能验证 |

离线编译的完整方法复用[Editor 脚本离线编译参考](unity-editor-script-offline-compile-verification.md)。遇到引用重复时检查实际程序集布局和 facade/module 集合，不依据文件名把所有 DLL 直接合并；遇到 SDK restore 失败时先区分依赖准备与代码错误，不为了让离线工程通过去改生产 API。

Unity 启动失败先看版本、许可证 IPC、工程锁、包恢复和编译日志。进程 PID、命令退出为零、日志出现 Editor 启动信息，都不足以独立证明测试通过；结合本轮新结果文件、唯一成功标记、预期断言数和退出码判断。

### 3.11 为 Undo 自检建立环境基线

隔离测试可以在启动完成后的回调执行：先创建一个探针对象、注册创建 Undo、Flush、隔离后续组并执行一次 Undo，断言探针已消失；再清空该隔离工程的 Undo 历史开始工具测试。若最小基线不通过，先查环境或测试时序；基线通过而工具失败，再检查工具自己的分组和收束顺序。

测试工程与正式工程分开，新场景和临时资源只在隔离工程中创建；不要为自检关闭用户未保存场景或清除用户的 Undo 历史。通过延迟回调启动测试时，由测试逻辑显式退出；命令行提前退出可能让回调尚未执行。

测试脚本可通过反射设置窗口私有选项并调用执行函数，适合回归已有工具，缺点是字段或方法改名后需要维护。涉及内部 Unity API 的诊断代码要单独标明版本依赖；功能断言优先检查场景和资产的可观察状态。

### 3.12 常见问题与处理顺序

| 现象 | 优先检查 | 处理思路 |
| --- | --- | --- |
| 模型重叠、闪烁 | 原 Renderer 与新子 Renderer 是否同时绘制 | 确认清理开关；完整结果就绪后再清理 |
| 原节点变空但没有结果 | 是否先删来源、后保存，或 Mesh 仍是临时对象 | 调整提交顺序，增加持久化及对象断言 |
| 某些距离消失 | LOD 数组、Bounds、layer、相机剔除 | 修复范围内引用，分距离与姿态验证 |
| 删除调用后组件仍在 | 组件依赖和 Prefab 限制，Unity 日志 | 检查删除结果，当前项回滚 |
| 父子同选后重复生成 | 是否按名称或 Mesh 去重，是否边遍历边新增 | 按 Renderer 身份去重，固定来源列表 |
| 一次 Undo 没恢复来源 | 最终分组是否在刷新/选择前结束 | 先做 Undo 基线，再调整最终收束边界 |
| Redo 出现 Missing Mesh | Undo 时是否删除了成功资产 | 分离资产和场景寿命，明确清理契约 |
| 取消后半套结果 | 是否只停止循环，没有补偿当前项 | 安全点取消，逐项回滚资产与场景 |
| 文件重复覆盖 | 是否直接拼路径写资产 | 清理文件名并使用唯一新增策略 |
| 动画不再驱动拆分结果 | Animator/Timeline 仍绑定原路径或组件 | 明确支持边界，单独重绑或保留来源 |
| 蒙皮动画边缘消失 | Bone、Bind Pose 和 Bounds 是否一致 | 分别验证骨架和形变包围范围 |
| 只有离线编译报类型重复 | facade 与模块重复，或引用了旧同名源码程序集 | 按实际程序集布局收敛引用 |
| Unity 已启动但没有结果 | 早退、延迟回调、编译或许可证错误 | 看完整阶段日志，不把启动视为通过 |
| 仓库检查失败很多 | 修改前基线与本次 diff 是否一致 | 区分既有失败、环境阻塞和本次回归 |
| 中文写成问号或乱码 | PowerShell 到原生工具的编码边界 | 文件参数传递、显式 UTF-8、写后读回 |

## 4. 风险与不适用边界

- 几何正确不代表完整行为保真。自定义 Vertex Streams、额外权重格式、属性块、动画绑定、运行时缓存和脚本引用，需要项目级数据契约。
- 不要从单一骨骼和一个 BlendShape 权重断言，推导多骨骼、多 Frame 全 Delta 正确；测试名里写“可见”也可能仅检查 enabled。
- 保留原组件的重复执行通常会再次生成一套结果。若需要幂等更新，另行设计结果身份、更新规则与旧资产回收，不能顺手改成覆盖。
- 逐项事务只保证定义范围内的补偿。磁盘写满、权限变化、导入器回调或回滚删除失败，都需要额外注入和错误报告。
- 祖先 LOD 修复不等于整个项目引用迁移；普通 Prefab 测试不代表嵌套、Variant、Model Prefab 和各 Stage 全覆盖。
- 拆分子 Renderer 可能增加 Draw Call、组件数、资产数、内存和磁盘空间。没有基准测量时，不把“结构整理”表述为“性能优化成功”。
- 独立编译、最小工程测试、仓库门禁、生产视觉验收各自提供不同证据。任何一层通过都不能代替其他层。

## 5. 验证与回退

### 5.1 最小充分验证矩阵

| 范围 | 代表用例 | 通过条件 |
| --- | --- | --- |
| 输入和去重 | 空选择、父子同选、资产对象、静态/蒙皮混批 | 可定位拒绝或跳过；每来源处理一次 |
| 路径和命名 | 源目录、多来源目录、自定义、无效路径、重复运行 | 目录可解释，无旧资产覆盖 |
| 静态保真 | 非单位父变换、材质、静态标志、Renderer 设置 | 新对象的声明范围内状态一致 |
| 蒙皮保真 | 多骨骼、Bind Pose、多个 Shape/Frame、极限姿态 | 数据映射和实际形变正确 |
| 清理范围 | 开/关、Collider、脚本、既有子节点、依赖阻止删除 | 只清理声明组件；失败恢复来源 |
| LOD 和 Prefab | 多 LOD、普通实例、嵌套/Variant/Model/Stage | 支持范围内引用正确，无意外 Apply |
| 场景 Undo/Redo | 单项成功、混批局部失败、连续操作 | 一次 Undo/Redo 恢复声明范围且 Mesh 有效 |
| 异常和取消 | 空 SubMesh、中途取消、写入失败、删除失败 | 当前项无半成品，已提交项符合批次策略 |
| 持久化 | 保存、关闭、重开、重导入 | Mesh 仍存在且场景引用有效 |
| 显示和性能 | 实际材质、目标相机、LOD 距离、真实批量规模 | 视觉符合预期，性能结论有测量 |

建议按“静态检查 → 对应版本编译 → 隔离行为测试 → 正式工程代表场景”的顺序推进。新增修改引入新的未知后再扩大验证；已通过且没有新变化的检查不必机械重复。

### 5.5 回退与知识维护

逐项失败先执行该项补偿并验证来源恢复；用户回退成功场景时先 Undo，再按输出清单决定是否保留生成资产。需要 Redo 时保留资产，避免先删除后让场景恢复空引用。原有资产未被覆盖时也仍需保留版本控制基线，以恢复意外扩大到外部消费者的修改。

后续发现新问题，先在对应项目 Profile 保留复现、根因、修正和证据；可迁移且已验证的实现模式再补入本文，规范性要求仍引用现有 CORE ID，不另建同义规则。
