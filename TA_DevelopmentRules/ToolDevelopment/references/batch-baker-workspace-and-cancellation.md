# Editor 批量烘焙工作区与安全取消参考

> 类型：REFERENCE；适用范围：Unity Editor 中同时提供单个与批量模式的贴图、LUT、Cubemap、图集和其他资源烘焙/导出工具；使用前提：必须以目标项目的资源格式、Unity 版本、GPU API、导入链和输出消费者重新验证。本文补充 `TOOL-ARC-01`、`TOOL-UI-01`、`TOOL-OPS-01`、`TOOL-OPS-02` 与 `TOOL-VAL-02`，不另行定义平行强制规则。

## 1. 适用场景

本文适用于以下工具演进：

- 原工具只有单个资源烘焙，需要增加批量列表、自动命名和批量结果汇总；
- 工具同时包含输入、质量参数、输出目录、状态说明和高级诊断，界面已难以扫描；
- 单项内部包含 GPU 渲染、Readback、编码、文件写入或资源导入，希望提供真实而非装饰性的进度与取消；
- 一项会生成多个配套文件，需要避免取消或异常留下半套正式输出；
- 批量任务允许单项失败后继续，但取消后应停止当前项和后续项。

以下情况不宜直接套用：

- 处理对象彼此存在强依赖，后项必须读取前项正式输出；
- 取消后无法恢复全局状态或资产一致性；
- 每项会修改共享 Scene、Prefab、Importer 或数据库记录，且没有快照、Undo 或事务边界；
- 工具核心其实是长生命周期预览、Scene Handle 或实时监听，应先按预览工具拆分，而不是塞入批量烘焙窗口。

## 2. 前提与依赖

### 2.1 先冻结单项行为

批量模式应复用已经验证的单项执行函数，而不是复制一份简化算法。扩展前先记录：

| 契约 | 需要确认的内容 |
| --- | --- |
| 输入 | 类型、必需字段、共享参数、逐项参数、资源是否必须位于 `Assets/`。 |
| 输出 | 扩展名、颜色空间、压缩、配套元数据、导入设置、命名后缀。 |
| 覆盖 | 是否覆盖、覆盖哪些文件、是否二次确认、是否可恢复。 |
| 进度 | 单项有哪些可观察阶段，哪些阶段会阻塞 Editor 主线程。 |
| 取消 | 哪些检查点取消安全，取消当前项后正式文件是否保持旧版本。 |
| 结果 | 成功、失败、跳过、未处理如何计数，错误如何定位到源资源。 |

单个模式继续保留保存窗口和自定义文件名时，批量模式可以使用自动命名；两者属于不同交互入口，但最终必须调用相同校验和烘焙实现。

### 2.2 区分窗口状态与执行状态

窗口字段负责保存用户配置，不应成为批量执行期间不断变化的隐式输入。开始执行前先构建不可变计划，计划项至少包含：

```text
Source object
Resolved output path(s)
Per-item adapter/options（如有）
Overwrite state
Stable display label
```

执行期间只消费计划；不要在循环中重新读取 Selection、当前 Project 目录、当前高亮对象或可被用户修改的列表。

## 3. 实现或排查步骤

### 3.1 顶部只保留一级工作模式

同时支持单个与批量时，推荐在窗口顶部使用稳定的分段模式：

```text
[单个烘焙] [批量烘焙]
```

界面按以下层级组织：

1. 一级模式：单个/批量，只决定输入方式和主操作。
2. 模式输入：单个 ObjectField，或批量资源列表、添加选择、清空和预检。
3. 公共参数：质量、颜色空间、Padding、曝光等两种模式共用配置。
4. 输出位置：Project 文件夹 ObjectField、可编辑路径和实际解析目录。
5. 主操作：当前模式只显示一个明确的主要按钮。
6. 结果与说明：历史输出、失败详情、长说明和高级诊断默认折叠。

不要同时显示单个输入、批量列表和两套执行按钮，也不要用第二层大折叠组重复当前一级模式。模式切换只改变显示，不清空已填写字段。

### 3.2 批量输入列表围绕资源对象设计

批量列表优先保存强类型 Unity 对象，而不是字符串路径。常用交互包括：

- 直接拖入多个同类型资源；
- 从 `Selection.objects` 中按精确类型添加；
- 去重后添加，不因同名资产误判为同一对象；
- 清空列表是显式操作；
- 列表中的空项、重复项在执行前阻断，而不是运行到一半才报错。

去重可使用 `GetInstanceID()` 做当前 Editor 会话内判断；长期保存或跨会话计划需要使用 GUID/GlobalObjectId 等稳定身份。输出冲突应以解析后的完整路径做不区分大小写比较，不能只比较源对象名称。

### 3.3 先构建计划，再开放批量按钮

推荐让“批量预检”和按钮禁用状态调用同一个 `TryBuildBatchPlan`：

```csharp
private bool TryBuildBatchPlan(
    string outputDirectory,
    out List<BatchItem> plan,
    out string error)
{
    plan = new List<BatchItem>();
    error = string.Empty;

    // 1. 检查共享参数和输出目录。
    // 2. 检查空项、重复源和源资源特定约束。
    // 3. 生成安全文件名和完整输出路径。
    // 4. 拒绝同一批次内的输出路径冲突。
    // 5. 记录已有正式输出数量，供覆盖确认使用。
    return true;
}
```

自动文件名先对资源名执行 `Path.GetInvalidFileNameChars()` 清洗，再追加稳定后缀和扩展名。批量模式不应为每项打开 `SaveFilePanel`；这会破坏连续处理，也无法提前发现输出冲突。

预检至少显示：

```text
可处理数量
实际输出目录
已有同名输出数量
第一个阻断错误（或可定位错误列表）
```

### 3.4 覆盖确认只做一次

计划构建完成后统计所有正式输出和配套文件。只要存在覆盖，开始前统一确认：

```text
将覆盖 N 项已有输出
[开始并覆盖] [取消]
```

不要在循环中逐项弹确认框。逐项确认会让批量任务无法无人值守完成，取消语义也会混乱。若不同项需要不同覆盖策略，应把策略加入计划或列表，而不是临时提问。

### 3.5 让执行层报告真实阶段

窗口只能知道“第几项”，真正的阶段进度应由单项 Utility 回调：

```csharp
internal delegate bool BakeProgressHandler(
    string stage,
    float normalizedProgress);
```

Utility 在安全检查点报告，例如：

```text
解析输入
构建 GPU 中间结果
渲染 Mip/Face/Tile
GPU Readback
校验像素
编码输出
提交正式文件
刷新 Unity 资源
完成
```

窗口将单项进度映射为批量总进度：

```csharp
float batchProgress =
    (itemIndex + Mathf.Clamp01(itemProgress)) / itemCount;
```

进度文字同时显示 `当前序号/总数`、源资源名和阶段，避免只有百分比却不知道卡在哪一步。

### 3.6 取消只发生在一致性检查点

`DisplayCancelableProgressBar` 返回 `true` 只代表用户提出取消请求。推荐由 Utility 在安全检查点抛出 `OperationCanceledException`，由批量窗口统一捕获：

```csharp
if (progressHandler != null && progressHandler(stage, progress))
    throw new OperationCanceledException();
```

典型边界：

- GPU 命令提交、同步 Readback、图像编码、磁盘写入和 `AssetDatabase.Refresh` 可能阻塞主线程；用户点击取消后，要等该调用返回才能进入下一个检查点。
- 正式文件提交前的取消应丢弃当前临时结果。
- 正式文件已完整提交后的取消，应把当前项计为成功，再停止后续项，不能把已经落盘的结果标成失败或未处理。
- 取消批次后保留此前完成项，并明确报告当前项和后续项的边界。

不要用后台线程直接调用 UnityEngine、AssetDatabase、RenderTexture 或大部分 Editor API。需要真正异步时，先将纯 CPU/文件步骤与 Unity 主线程步骤分离，再定义线程安全接口。

### 3.7 多文件输出使用临时文件提交

一项生成 EXR + JSON、纹理 + 元数据或其他配套文件时，推荐事务式提交：

```text
写临时 EXR
写临时 JSON
校验两者完成
最后覆盖正式 EXR
最后覆盖正式 JSON
finally 删除临时文件
```

临时文件应与当前任务唯一关联，异常与取消都在 `finally` 清理。正式输出只有在整套文件准备完成后才覆盖，避免新 EXR 配旧 JSON 或相反。

单文件输出也应把最后一次取消检查放在写入前。文件写入完成后不再抛“取消导致失败”；若用户此时请求取消，只停止后续项。

事务提交不能代替版本控制。两个正式文件依次覆盖时仍存在极小的进程崩溃窗口；高价值资产需要原子替换 API、备份或项目级恢复策略。

### 3.8 单项失败与用户取消使用不同转换

推荐批量状态转换：

```text
Ready -> Running(item)
Running -> Succeeded -> Next item
Running -> Failed -> Record error -> Next item
Running -> CancelRequested -> Canceled -> Stop batch
Running -> Committed + CancelRequested -> Succeeded -> Stop batch
```

最终汇总至少包含：

```text
总数
成功
失败
跳过（如果计划支持）
未处理
是否由用户取消
每个失败项的源资源与错误摘要
最后成功输出路径
```

单项异常可继续处理后续项；共享依赖失效、输出目录不可写或图形设备丢失等全局错误是否立即中止，应由具体工具定义，不能无条件继续制造重复失败。

### 3.9 窗口与 Utility 保持单向依赖

推荐职责：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Window | 模式、序列化字段、列表、预检展示、覆盖确认、进度 UI、结果汇总。 | GPU 算法、编码细节、正式输出格式。 |
| Plan/Validation | 解析输入、命名、冲突、逐项前置条件。 | 写文件和改变资产。 |
| Bake Utility | 单项真实烘焙、资源生命周期、阶段回调、输出校验。 | Selection、窗口折叠状态、批量列表。 |
| Output/Import | 临时文件、正式提交、导入配置、定位结果。 | 重新决定用户输入。 |

旧单项 API 可通过可选回调保持兼容：`Bake(request, progressHandler = null)`。没有外部回调时，Utility 可以继续显示单项进度；批量传入回调时，由窗口拥有总进度条并在 `finally` 清理。

### 3.10 用原始结果验证烘焙正确性

窗口显示成功、文件存在和 Unity Inspector 缩略图都不能证明输出正确。根据输出类型增加最接近真实数据的校验：

- EXR/LUT：检查浮点通道有限、非全黑、范围和代表性色块；
- Atlas：检查尺寸、Face/Mip 布局、元数据和边缘 Padding；
- sRGB/Linear 纹理：检查实际 `GraphicsFormat` 和导入后采样语义；
- 多文件输出：检查正式文件来自同一计划项和同一提交；
- 目标 DCC 资源：在真实目标版本中导入并执行代表性 A/B。

静态编译和 `git diff --check` 只能证明源码层，不替代 GPU 烘焙、像素检查和消费者验证。

## 4. 风险与不适用边界

| 问题或反模式 | 典型后果 | 解决方式 |
| --- | --- | --- |
| 单个与批量字段同时展开 | 美术不知道先填哪组，容易点错按钮。 | 顶部一级模式；公共参数只保留一份。 |
| 只在窗口循环外显示 0/100% | 无法定位 GPU、编码还是导入阶段卡顿。 | Utility 报告真实阶段和单项归一化进度。 |
| 每项打开保存窗口 | 批量被退化成人工重复操作。 | 输出目录 + 自动安全命名 + 执行前冲突预检。 |
| 用名称判断重复源 | 不同目录同名资产被误判，或同一资产重复进入。 | 源身份与输出路径分别去重。 |
| 取消后删除全部已完成结果 | 用户丢失已成功的长耗时产物。 | 保留已提交项，只清理当前临时文件和未处理计划。 |
| 取消发生在正式文件写到一半 | 产生损坏或半套输出。 | 写前检查；多文件先临时写完再提交。 |
| 单项异常直接终止全部 | 一个坏资源阻塞其他有效资源。 | 记录可定位失败并继续；仅全局错误中止。 |
| 捕获所有异常后报告完成 | 结果计数失真，Console 与窗口状态矛盾。 | 区分失败、取消、未处理，最终统一汇总。 |
| 循环内频繁全工程 Refresh | 导入开销随项目规模放大。 | 能集中时集中刷新；必须逐项导入时明确成本并验证取消边界。 |
| 把按钮禁用逻辑和预检各写一套 | UI 显示可执行但点击后失败，规则逐渐漂移。 | 两处复用同一个计划构建函数。 |
| 将“可取消”理解为随时立即停止 | 阻塞 API 期间点击无响应，被误判为卡死。 | UI/README 明确取消在下一个安全检查点生效。 |

## 5. 验证与回退

### 5.1 最小验证矩阵

| 类别 | 用例 | 通过条件 |
| --- | --- | --- |
| 模式 | 单个/批量来回切换 | 只显示对应输入和按钮；公共字段、列表和结果不丢失。 |
| 空输入 | 无单项、空列表、列表空项 | 主按钮禁用或执行前阻断，提示可行动。 |
| 重复 | 同一源重复、同名不同源、清洗后同名 | 源重复与输出冲突分别报告。 |
| 输出 | Project 目录、外部目录、不存在目录、只读目录 | 解析状态正确；不隐式写入错误位置。 |
| 覆盖 | 无覆盖、部分覆盖、全部覆盖 | 只确认一次，数量准确，取消确认不写文件。 |
| 失败 | 中间项校验失败、烘焙异常、写入异常 | 失败项可定位；策略允许时后续项继续。 |
| 取消 | 首项前、GPU 阶段后、写入前、当前项提交后 | 计数与正式文件一致；临时文件清理；后续项未执行。 |
| 多文件事务 | 第二个配套文件写入失败 | 旧正式输出保持，或回退边界明确；不留下半套新结果。 |
| 输出内容 | Identity/灰阶/RGB/HDR、Face/Mip、元数据 | 原始像素/布局与消费者 A/B 均通过。 |
| 生命周期 | 窗口重开、Domain Reload、异常退出 | 无残留进度条、临时 RenderTexture、事件或临时文件。 |

### 5.2 分层验证顺序

1. 运行目标 asmdef 的定向编译，要求新增代码 `0 Warning / 0 Error`。
2. 运行 UTF-8、尾随空白、相对链接和 `.meta` 检查。
3. 在 Unity 中打开窗口，验证模式、折叠、列表和序列化状态。
4. 用两个最小资源执行完整批次，再验证中间项失败和取消。
5. 检查正式文件、临时文件、导入设置、结果计数和日志。
6. 使用真实 DCC/Shader/材质消费者执行代表性视觉 A/B。

### 5.3 回退策略

- UI 重组应只改变显示和工作区选择，不改变旧序列化字段、单项输出或菜单；出现排版问题可回退模式属性而不回退执行逻辑。
- 新批量入口失败时，保留原单项入口作为可用回退，不复制另一套算法。
- 多文件事务失败时清理本次临时文件；旧正式输出是否保持必须由提交策略验证。
- 实际 GPU/目标 DCC 未验证时，只能声明静态编译和计划逻辑完成，不能把批量产物正确性标记为已验收。
