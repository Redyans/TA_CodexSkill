# 工具开发技术参考｜2026-11-10

> 类型：REFERENCE；适用范围：Unity Editor 的 RT 颜色诊断、可恢复预览、已验证版本恢复。使用前提：以目标项目 API、图形格式、显示颜色域与生命周期重新验证。
> 本文提炼会话中的方法，不新增强制规则。项目菜单、格式与验证次数见[工具 Profile](../../Profiles/ProjectACG/CodexDaily/Development_Profile_2026-11-10.md)；截图和模糊渲染流程见[Shader 参考](../../../ShaderDevelopment/references/CodexDaily/Development_Reference_2026-11-10.md)。

## 1. 分离 RT 数据、颜色解释和最终显示

### 适用场景

RT 在 Inspector、Game View 或 UI 中发灰、变暗，无法判断是捕获、滤波、颜色转换还是显示层造成。

### 前提与依赖

明确问题出现在哪个观察位置，记录捕获时机、实际 RT 尺寸、graphicsFormat、sRGB 标记、项目颜色空间与显示消费者。引用[工具入口](../../README_Tech_TAToolDevelopmentRules.md)的 `TOOL-ARC-01`、`TOOL-OPS-03`、`TOOL-VAL-02` 和[Shader 入口](../../../ShaderDevelopment/README_Tech_URPShaderDevelopmentRules.md)的 `VAL-02`。

### 实现或排查步骤

1. 先让用户定位观察点：原始截图、模糊后 RT、Inspector 预览或最终 UI。若问题在 UI 之前，先排除 UI 遮色/混合因素。
2. 保留同帧原图，并与滤波结果对比，避免重新截屏引入时间、相机和场景变化。
3. 显示 RT 格式与 sRGB 声明，同时回读像素。不要让诊断预览自身隐式转换成为新的误差来源。
4. 对同一批原始数值提供两种解释：A 视为已编码 sRGB；B 视为 Linear 后转换为 sRGB。若某一解释接近原画面，只作为定位线索，还需对照同帧已知输入。
5. 提供图片预览、点击取点、刷新读数和导出对照图，让美术能把颜色现象与像素数据对应起来。
6. 用均匀灰阶与已知色块区分局部对比下降和整体传递函数错误。比如“已编码数值被再当 Linear 编码”可抬亮中间调，但前提是实际数据确实经历该错误链；不能只凭 RT 标记确定根因。

### 风险与不适用边界

Inspector 外观不是原始数据证据；descriptor 构造默认行为依赖版本。工具自身通过测试，不代表用户场景已诊断。不要为了消除发灰直接叠加 Gamma 校正，而未先确认捕获 API 的实际输出域。

### 验证与回退

用 RGBA/BGRA 已知通道顺序测试原始回读、两种显示解释和导出；检查源 RT 未被改写。保留原输出与未加工读数，以便关闭诊断恢复。来源：S2 消息 7–21。

## 2. 让“跳过处理”成为可恢复的临时预览

### 适用场景

需要在编辑器 Play Mode 中查看原图与处理结果，并在切换实例或关闭窗口后恢复正常显示。

### 前提与依赖

有可靠的处理前备份，明确目标实例与预览资源所有权。已有要求见[工具入口](../../README_Tech_TAToolDevelopmentRules.md)的 `TOOL-CMP-01`、`TOOL-ARC-02`、`TOOL-UI-02`。

### 实现或排查步骤

1. 开启跳过处理时，将保留的同一张原图用于输出，而非重新捕获场景。
2. 区分“原图备份”“处理后结果”“当前输出”，保证窗口显示用户实际选择的阶段。
3. 将恢复动作绑定到关闭开关、切换实例、窗口关闭等生命周期；不要把临时诊断选择误存为正式资源配置。
4. 误回退后先检查“入口、底层实现、预览”分别还剩什么，只恢复缺失接线，避免重新生成仍然存在的工具。
5. 编辑态可检查已有有效 RT，Play Mode 可检查运行实例；这不自动意味着 Player 构建里有诊断窗口。

### 风险与不适用边界

没有原图备份时不能声称能恢复同一帧。更改运行中 RT 格式可能重建并丢失内容，需重新创建或捕获。关闭窗口后的恢复需要实际验证，不能只凭开关能显示原图推断。

### 验证与回退

检查开启、关闭、切换实例、窗口关闭和反复操作；数值对比原图与恢复输出，确认无源 RT 修改、资源泄漏或临时状态残留。来源中仅部分生命周期有报告，Domain Reload、异常与打包验证缺失，应列为补验。来源：S2 消息 16–31。

## 3. 浮点 RT 回读、导出与诊断阈值

### 适用场景

截图或处理链升级为浮点格式，需要检查精度是否保留，或诊断把暗部误报成黑图。

### 前提与依赖

确认目标格式可用于捕获、渲染与回读；截图、备份、所有中间 RT 保持明确且一致的格式契约。验证边界沿用 `TOOL-VAL-01`～`TOOL-VAL-03`，不把编辑器通过推广为所有平台支持。

### 实现或排查步骤

1. 支持浮点原始 RGBA 读数，保留超出 0–1 的数据；显示和导出路径单独声明其范围。
2. SDR PNG 和常规对比预览可用于 0–1 范围内的显示比较，若执行截断，不用它们判断 HDR 精度是否保存。
3. 端到端检查捕获、每次滤波、中间缓存与原图恢复，避免主 RT 升级但中间仍降到 8 位。
4. “黑图”判定同时看格式、颜色域和对应已知输入。在线性域暗部数值小是正常现象，不能机械复用 sRGB 数值阈值。
5. 将格式提高带来的内存成本与发灰诊断分开；高精度格式并不自动修复颜色转换错误。

### 风险与不适用边界

某个 API 在一个桌面图形后端能写浮点 RT，不代表其他设备同样可靠。浮点容器也不意味着截图包含色调映射前 HDR 数据。具体回读 API 与格式降级策略在来源文字中未完整给出，不补造实现。

### 验证与回退

用已知颜色比对整数截图与浮点线性读数，记录容差和颜色域；逐级检查滤波没有非预期量化。源数据、预览和导出各自验收。回退需同时恢复相关 RT 格式并重新捕获。来源：S2 消息 32–40。

## 4. 按内容与验证身份恢复被回退的改动

### 适用场景

代码或工具入口疑似意外回退，且存在先前验证过的版本。

### 前提与依赖

已知预期功能清单、当前文件和可识别的历史备份。源码恢复的兼容性与证据要求沿用 `TOOL-CMP-01`、`TOOL-OPS-03`，Shader 变体沿用 `CTL-02`、`VAL-03`。

### 实现或排查步骤

1. 对比具体特征和内容，不只比较文件名、修改时间或行数；行数和开关数量只能帮助定位。
2. 比较时说明是否忽略换行等无关差异，防止把内容身份与字节哈希身份混为一谈。
3. 分清仅入口丢失、功能代码丢失、全文件回退；恢复最小缺口，并保留现有 `.meta`/GUID。
4. 输出恢复后状态、当前检查与历史检查的区别。恢复到历史已测内容，可以说明历史证据关联，但不能表述为本次又做了 GPU 测试。
5. 迁移引起的失败还要检查依赖闭包与当前相对路径；相关资产检查引用[现有集成清单](../tool-integration-checklist.md)。

### 风险与不适用边界

没有读取到备份、不能证明版本身份或存在其他修改时，不可整文件覆盖。当天来源没有确认误回退的具体操作原因，不将它归咎于版本控制或某个工具。

### 验证与回退

恢复后进行目标编译、接口和内容检查；涉及新依赖或环境变化时补行为测试。保存恢复前差异以便回退；不能用旧验证数字覆盖当前未验证项。来源：S1 消息 178–211、S2 消息 28–31。
