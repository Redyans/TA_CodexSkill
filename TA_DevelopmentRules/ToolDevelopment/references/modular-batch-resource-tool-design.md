# 模块化批量资源 Editor 工具设计参考

> 类型：REFERENCE；适用范围：Unity Editor 中同时处理模型/GameObject、材质和贴图的模块化扫描、批处理与转换工具；使用前提：必须以目标项目的 Unity 版本、资源结构、程序集和实际消费者重新验证。
>
> 关联规则：`TOOL-CLS-01`、`TOOL-CMP-01`、`TOOL-ARC-01`、`TOOL-UI-01`、`TOOL-OPS-01`、`TOOL-OPS-02`、`TOOL-VAL-02`。

## 1. 适用场景

本参考适用于把单一用途的 EditorWindow 扩展为多个资源模块共用的批量工具，例如：

- 模型/GameObject：批量读取或修改 `Renderer` 相关设置。
- 材质：扫描材质引用、检测 Material Variant，并在满足安全条件时转换。
- 贴图：通过 `TextureImporter` 批量修改导入设置。
- 输入同时来自 Hierarchy 当前选择、Project 当前选择和指定目录递归扫描。
- 多个模块需要共用目标范围、执行入口、结果展示和日志，但每个模块拥有不同操作与风险。

以下情况通常不宜强行合并到一个窗口：

- 各功能没有共同输入、执行流程或用户角色，只是菜单分类相同。
- 某个模块需要复杂预览、Scene Handle、长生命周期缓存或独立工作区。
- 某个功能涉及自动导入、构建回调或运行时组件，而其他模块仅是手动 Editor 操作。
- 为了“统一”必须引入大量无效状态、空面板或跨模块条件分支。

合并工具的判断标准不是代码是否能放进同一文件，而是用户是否能用同一套“选择范围 → 设置 → 执行 → 查看结果”心智模型完成任务。

## 2. 前提与依赖

### 2.1 先冻结模块契约

每个模块至少明确以下内容：

| 契约维度 | 需要确认的问题 |
| --- | --- |
| 目标类型 | 处理 GameObject、Prefab、Material、Texture，还是对应 Importer？ |
| 选择来源 | Hierarchy、Project 直接选择、目录递归是否都支持？ |
| 子级范围 | 是否包含子节点、未激活节点、Prefab 嵌套对象？ |
| 操作类型 | 只读检测、对象字段写入、资产转换、Importer 重导入分别是什么风险？ |
| 可写边界 | Scene 对象、独立资产、导入模型子资源、Packages 资源分别如何处理？ |
| 结果身份 | 按对象引用、主资产 GUID、子资源 ID、资产路径还是 Renderer 槽位去重？ |
| Undo/回滚 | Unity Undo 是否覆盖全部副作用？重导入或资产保存如何恢复？ |
| 验证入口 | 需要验证窗口、Scene/Prefab、材质参数、GUID、Importer 还是最终画面？ |

不要先做模块按钮再补语义。模块的目标、状态、执行器和结果模型没有冻结时，UI 切换只会隐藏职责混乱。

### 2.2 验证 Unity API 与项目边界

`Material.isVariant`、`Material.parent`、Prefab API、Importer 字段以及 Undo 行为可能随 Unity 版本和资源类型变化。实现前需要确认：

- 目标 Unity 版本确实提供所需 API。
- 工具位于 `Editor` 目录或 Editor-only asmdef。
- 目标资产是否可写，是否来自 `Assets/`、`Packages/`、只读包或版本控制锁定目录。
- 项目是否已有自定义导入器、ShaderGUI、AssetPostprocessor 或资源生成链覆盖同一字段。
- 修改共享材质或 Importer 后有哪些 Prefab、Scene、构建产物和视觉结果会受影响。

## 3. 实现或排查步骤

### 3.1 用“模块描述”组织状态和行为

模块应当是完整的功能边界，而不只是一个枚举标签。建议每个模块显式拥有：

| 模块组成 | 职责 |
| --- | --- |
| 模块 ID 与短名称 | 用于顶部切换和状态保存。 |
| 选择收集器 | 从 Selection 与目录得到当前模块真正可处理的对象。 |
| 操作集合 | 只暴露对该目标类型有效的操作。 |
| 独立设置状态 | 切换模块时保留各模块上次参数，避免共用字段互相污染。 |
| 校验器 | 输出可处理、跳过、只读、冲突和高风险目标。 |
| 执行器 | 只接收已校验计划，不重新猜测输入范围。 |
| 结果视图 | 展示成功、失败、跳过、引用位置和回滚信息。 |

可以在简单工具中使用同一个操作枚举，但模块到操作的映射必须显式。执行层仍需按目标类型分流，不能让 Renderer 操作落到 Importer，也不能依赖 `default` 分支静默跳过错误组合。

当模块继续增加时，优先把“收集、校验、执行、结果”拆成模块策略或独立类，而不是持续扩大窗口类中的 `switch`。只有状态少、流程短、单文件仍可清晰审计时才保留单文件实现。

### 3.2 使用紧凑而稳定的窗口布局

模块化批处理工具可采用以下信息层级：

```text
顶部工具栏：工具名 | 模块切换 | 全局快捷操作
用途说明：一行说明处理对象与公共范围
1. 目标范围
2. 当前模块设置
3. 执行与数量
4. 当前模块结果
```

设计经验：

1. 模块切换属于一级导航，放在窗口顶部工具栏，用短名称按钮或紧凑下拉框表示；不要再占用一个大型 HelpBox。
2. 顶部只放全局且高频的动作，例如切换模块、取当前目录、刷新；模块私有参数留在内容区。
3. 用途说明控制在一行，回答“处理什么、范围是什么”。共享资产风险放在对应破坏性操作附近，不要全部堆到总说明。
4. 目标范围和执行结构保持稳定；切换模块时只替换标签、操作项、可处理数量和结果区，降低用户重新理解成本。
5. 只显示当前模块有效的设置。隐藏无效字段比禁用大量无关字段更清晰。
6. 执行按钮写明动作，例如“检测材质变体”或“执行贴图导入设置”，避免只写“执行”。
7. 选择数量必须由实际收集器计算，不能用 `Selection.objects.Length` 冒充可处理数量。
8. 破坏性操作使用就近 Warning 和确认框；只读扫描不应弹出不必要确认。
9. 如果顶部工具栏需要滚动时始终可见，应放在主 ScrollView 外；窗口内容再独立滚动。
10. 用最小窗口宽度和窄窗口实测按钮是否截断，模块名称优先使用“模型”“材质”“贴图”等短词。

### 3.3 按资源类型收集选择，不要混用 Selection API

Hierarchy 与 Project 的 Selection 表面相同，实际对象类型和持久化语义不同。建议按模块定义收集路径：

| 模块 | 当前选择 | 目录递归 | 关键点 |
| --- | --- | --- | --- |
| 模型/GameObject | `Selection.gameObjects` | `FindAssets("t:Prefab")` 后加载目标 | 对子节点使用 `GetComponentsInChildren(..., true)`；区分 Scene 对象、可写 Prefab 与导入模型资产。 |
| 材质 | 选中 GameObject 的 `Renderer.sharedMaterials`，以及 `Selection.objects` 中直接选中的 Material | 扫描 Prefab 引用和 `FindAssets("t:Material")` | 保留 Renderer 路径与槽位；不要访问 `renderer.material` 产生实例材质。 |
| 贴图 | 遍历 `Selection.objects`，由资产路径取得 `TextureImporter` | `FindAssets("t:Texture")` 后取得 Importer | `Selection.gameObjects` 无法覆盖 Project 中直接选中的贴图。 |

收集阶段建议遵守以下顺序：

1. 读取 Selection 和目录对象引用。
2. 将对象解析为模块目标类型或 Importer。
3. 过滤空路径、目录对象、类型不匹配、只读和不可处理目标。
4. 用稳定身份去重。
5. 记录来源和引用位置。
6. 只生成执行计划，不在收集时写资产。

去重不能一律只用资产路径。独立主资产可使用规范化路径或 GUID；FBX 等文件可能包含多个子资源，材质子资源应使用对象引用、`GlobalObjectId` 或“主资产 GUID + local file ID”区分。Renderer 材质引用还要保留槽位，避免去重后丢失使用位置。

### 3.4 模型/GameObject 模块区分 Scene 与资产

处理 Renderer 设置时可以统一递归收集 Renderer，但写回路径需要分开：

- Scene 对象：写入前记录 Undo，修改后 `SetDirty`，并标记对应 Scene dirty。
- 独立 Prefab：在隔离内容或临时实例中修改，保存回原 Prefab，并确保 `finally` 清理临时对象。
- 导入模型资产：通常不是可直接保存的 Prefab；需要修改模型导入设置时应走 `ModelImporter`，不能把 FBX 当成普通 `.prefab` 覆盖。
- Prefab Instance：先明确修改实例覆盖还是修改源资产，不能由工具静默决定。

对选中父节点批处理时默认扫描未激活子节点更符合资产治理预期，但 UI 应写清“包含子节点”。重复选择父子节点时，应避免同一 Renderer 被重复写入和重复计数。

### 3.5 材质变体采用“先检测，后受控转换”

材质变体处理至少拆成两个动作：

1. 检测：只读扫描并列出变体、Parent、资产路径、引用 Renderer/层级/槽位和可转换状态。
2. 转换：只处理通过可写校验的候选，执行前显示数量和共享资产影响。

检测结果建议包含：

- Material 对象身份和资产路径。
- `isVariant` 与 `parent`。
- 是否为独立主资产。
- 可转换或仅检测原因。
- 使用位置集合。
- 转换后的状态和错误。

通常可以原地转换的候选应同时满足：

- 位于项目可写的 `Assets/` 范围。
- 是独立 `.mat` 主资产。
- 当前仍为 Material Variant。
- 不属于 Packages、FBX/模型内嵌子资源或其他只读来源。

Packages 材质和模型内嵌材质可列入报告，但默认只检测、不改写。这样能把“看见问题”和“安全修复”分开。

受控转换可采用以下流程：

1. 在修改前读取当前解析后的材质状态并建立快照。
2. 注册完整对象 Undo。
3. 解除 Parent。
4. 把快照中的最终材质状态写回普通材质。
5. 标记 dirty 并保存。
6. 验证 `isVariant == false`，并比较转换前后的 Shader、属性、Keyword、Render Queue、GI/Instancing 等关键状态。

材质是共享资产。确认文案需要明确：路径和 GUID 即使不变，所有引用该材质的 Scene、Prefab 和 Renderer 都会看到新状态。不要用“只改选中模型”弱化共享影响。

属性快照不能代替视觉验证。不同 Unity/Shader 组合下，继承值、Override 状态、Keyword、隐藏属性或自定义 ShaderGUI 数据可能有差异；应使用代表性测试材质检查转换前后 Inspector 与目标画面。

### 3.6 贴图模块围绕 TextureImporter 工作

贴图导入设置属于资产导入契约，不是 Texture 对象的普通字段编辑。建议：

- 从资产路径取得 `TextureImporter`，无法取得 Importer 的对象直接跳过并说明原因。
- 只修改当前操作对应的字段，避免顺便覆盖 Texture Type、平台 Override、压缩、尺寸或颜色空间。
- 写入前比较旧值，只对发生变化的资源重导入。
- 小批量可逐项 `SaveAndReimport`；大批量需要评估统一写入、进度、重导入成本和异常恢复，避免无条件每项刷新全工程。
- 汇总“候选数、实际变化数、重导入数、跳过数和失败数”，不要把扫描数量当作修改数量。
- 平台 Override、Sprite 子资源、法线贴图和自定义 Importer 需要独立边界测试。

### 3.7 把执行流程建模为可观察状态转换

推荐将一次执行理解为：

- State：当前模块、模块参数、选择开关、目录、上次结果。
- Input：Selection 快照、目录快照、用户确认。
- Transition：收集 → 校验 → 计划 → 确认 → 执行 → 汇总。
- Effect：对象字段写入、Prefab 保存、材质修改、Importer 重导入。
- View：范围说明、数量、风险、进度、结果和错误。

这样可以避免在 `OnGUI`、Layout 或 Repaint 阶段执行副作用，也便于重放和测试。

执行前的计划至少给出：

- 扫描总数和去重后的目标数。
- 可处理、只检测、跳过和冲突数量。
- 会写入哪些对象或资产。
- 是否需要 Undo、保存、重导入或共享资产确认。

执行后至少记录：

- 成功、失败、跳过和未变化数量。
- 失败对象/路径与原因。
- 实际保存或重导入的资产。
- 是否可 Undo，以及 Undo 不能覆盖的部分。

### 3.8 按复杂度决定单文件还是拆分

单文件适合模块少、状态少、执行流程短且没有复杂报告的工具。出现以下信号时应按职责拆分：

- 窗口类同时承担多类 Selection 收集、资产 IO、转换算法和长结果列表。
- 新增模块需要复制大量 `switch`。
- 扫描与写入难以单独测试。
- 同一资产操作需要被菜单、Inspector 或其他工具复用。
- 日志、进度、取消、报告导出开始形成独立生命周期。

推荐依赖方向为：Window/State → Module Coordinator → Collector/Validator/Executor → Unity Asset API。UI 可以读取结果模型，但资产执行层不应反向依赖窗口绘制。

## 4. 风险与不适用边界

| 风险 | 常见错误 | 控制方式 |
| --- | --- | --- |
| 选择范围误判 | 只用 `Selection.gameObjects`，导致贴图和直接选中材质未处理。 | 每个模块使用自己的收集器，并显示实际可处理数量。 |
| 共享材质扩散 | 用户以为只影响选中 Renderer，实际修改了共享 `.mat`。 | 显示引用位置、共享警告、确认和 Undo；优先在测试资产验证。 |
| 材质实例泄漏 | 扫描时访问 `renderer.material`。 | 只读扫描使用 `sharedMaterials`。 |
| 子资源误改 | 把 FBX 内嵌材质当成独立材质覆盖。 | 校验主资产与扩展名；内嵌/Package 默认仅检测。 |
| Prefab/模型混淆 | 将导入模型资产按普通 Prefab 保存。 | 区分 `.prefab` 与模型导入资产，后者走 Importer 或只读报告。 |
| Undo 预期错误 | 认为 Save/Reimport、外部文件和所有 Prefab 写入都能完整 Undo。 | 明确 Undo 覆盖边界；高风险批量先用版本控制或副本。 |
| 批量导入卡顿 | 循环中对未变化资源反复 Save/Refresh/Reimport。 | 只写变化项，集中刷新，提供进度和耗时。 |
| 模块状态串扰 | 切换模块后沿用上一模块的操作或参数。 | 每个模块保存独立状态，切换时只解析该模块操作。 |
| UI 信息过载 | 总说明罗列全部范围和风险，模块区占用大量空间。 | 顶部紧凑导航，一行用途说明，风险就近展示。 |
| 去重丢信息 | 只按路径去重，合并多个子资源或 Renderer 槽位。 | 用稳定对象身份去重，引用位置单独累积。 |

本参考不建议将自动导入 Hook、构建回调、运行时修复或全工程后台扫描直接并入普通手动批处理窗口。若确有需求，应按高影响工具重新定义触发、禁用、幂等、性能和构建验证边界。

## 5. 验证与回退

### 5.1 最小验证矩阵

| 维度 | 代表性用例 | 通过条件 |
| --- | --- | --- |
| UI | 窄窗口、切换三个模块、滚动、Domain Reload 后重开 | 顶部切换清晰；无截断、错位和模块状态串扰。 |
| 空输入 | 未选择对象且未指定目录 | 不执行写入，给出可行动提示。 |
| Hierarchy | 选择带未激活子节点的根对象 | 只处理预期 Renderer，数量与结果一致。 |
| Project 直接选择 | 分别多选 Prefab、Material、Texture | 每个模块只收集有效类型，错误类型被跳过并说明。 |
| 目录 | 含子目录、重复引用、混合资源类型 | 递归范围正确，目标去重且引用位置不丢失。 |
| Scene/Prefab | Scene 对象、Prefab Asset、Prefab Instance | Dirty、Undo、保存目标和实例覆盖符合契约。 |
| 材质变体 | 独立 `.mat`、Packages 材质、模型内嵌材质 | 独立材质可受控转换；只读/内嵌目标仅检测。 |
| 材质保真 | 对比转换前后 Inspector 与目标画面 | Shader、关键参数、Keyword、Render Queue 和视觉结果符合预期。 |
| 贴图 | 已是目标值、需要修改、带平台 Override | 只重导入变化项，不覆盖未声明设置。 |
| 失败/取消 | 取消确认、单项异常、只读资产 | 不伪报成功；结果区分已完成、跳过和失败。 |
| 标识与引用 | 修改前后检查路径、GUID、引用 | 契约要求保留的标识和引用未变化。 |

### 5.2 分层验证顺序

1. 静态检查：UTF-8、API、菜单、序列化字段、无效操作映射、链接和 diff 空白。
2. Unity 编译：让 Editor 实际导入并编译受影响程序集。
3. 窗口验证：打开真实入口，检查布局、选择计数、模块切换和风险提示。
4. 资产验证：在测试 Scene/Prefab/Material/Texture 上执行代表性流程。
5. 视觉验证：材质或 Shader 相关变更使用目标模型、灯光和场景比较。
6. 性能验证：用接近真实规模的目录检查扫描、保存和重导入耗时。
7. 回滚验证：实际测试 Undo；Undo 不覆盖的副作用用版本控制或资产副本恢复。

### 5.3 回退与未验证项

批量写入正式资源前，优先在隔离目录或资产副本运行，并确保版本控制可恢复。材质共享引用、Importer 重导入、Prefab 保存和模型内嵌资源的 Undo 能力不应只凭 API 名称推断。

迁移本参考到其他项目时，需要重新确认：
