# Unity Editor 资源表格性能与缓存设计参考

> 类型：REFERENCE；适用范围：Unity Editor 的资源浏览器、检查表、材质/贴图列表及相似扫描工具。使用前以目标项目代码、Unity 版本和数据规模重新验证。
>
> 通用规范见 [工具开发模块](../README_Tech_TAToolDevelopmentRules.md) 的 `TOOL-CMP-01`、`TOOL-ARC-01`、`TOOL-ARC-02`、`TOOL-OPS-02`、`TOOL-VAL-01`、`TOOL-VAL-02`。本文提供实现选择和检查方法，不另建强制规则。
>
> 对应案例、具体函数、历史测试证据及尚未完成的宿主验证见 [ProjectACG Scene Explorer Profile](../Profiles/ProjectACG/scene-explorer-resource-table-performance.md)。案例中的算法测试不等于真实场景帧率结论。

## 1. 适用场景

资源列表出现“切到某页后持续卡顿”“滚动和输入越用越慢”“表格有数据但计数为零”“每次切回窗口都扫描”的问题时，可沿本文检查。可迁移到材质浏览器、动画资源目录、Prefab 审计表、Shader 变体选择器和资产批量修改窗口。

先把用户感知拆成不同阶段，避免用同一种优化处理全部问题。

| 现象 | 优先调查 | 可能的处理方向 | 验证重点 |
| --- | --- | --- | --- |
| 第一次打开明显停顿，之后流畅 | 扫描、资产加载、排序、首次元数据查询 | 限定范围、缓存共享解析、分批执行 | 冷启动耗时、峰值内存、取消边界 |
| 打开后不操作也持续卡 | 重绘、全表筛选、无条件刷新 | 缓存筛选、只画可见行、减少无效重绘 | 每次 GUI 事件耗时及分配 |
| 滚动卡，静止时正常 | 全行控件、平台格式计算、缩略图请求 | 虚拟化、按需缓存、预览调度 | 滚动期间新加载量、末行可达性 |
| 输入搜索时卡 | 每个字符扫描、字符串处理、Importer 读取 | 索引缓存、短路匹配、必要时防抖 | 搜索响应及筛选一致性 |
| 切回窗口卡一下 | `OnFocus` 导致全量扫描 | 分离元数据失效与资源集合失效 | 焦点变化时执行了哪些工作 |
| 批量应用卡 | 导入、保存、回调重复触发扫描 | 跳过未变项、汇总刷新、进度与失败策略 | 实际写入、部分失败、Undo |
| 数量、选择与表格对不上 | 控制流、不同筛选源、失效遗漏 | 单一筛选结果、明确分支、状态一致性 | 全部结果与可见结果的区分 |

## 2. 前提与依赖

### 2.1 先冻结工具的行为契约

按 `TOOL-CMP-01` 记录以下项目，再动性能路径。

- 扫描对象：当前场景、全部已加载场景、选择子树、项目文件夹，是否包含未激活对象和子资产。
- 统计语义：唯一资产数、引用次数、唯一使用对象数，三者分别是什么。
- 筛选语义：名称/路径/类型、布尔字段、大小写、空值和不可读取资源如何匹配。
- 选择语义：筛选后是否保留隐藏项选择，“全选结果”是全体匹配项还是当前页。
- 编辑语义：只读预览列、可写列、延迟写入、批量应用目标、Undo 和保存边界。
- 显示语义：排序、列宽、横纵滚动、标题、定位资源、定位首个使用者。

性能重构后，结果集合和写入范围也属于验收项。仅检查“窗口不卡”会漏掉错选资源、漏扫和错误计数。

### 2.2 理解 IMGUI 的调用频率

`OnGUI` 可能因 `Layout`、`Repaint`、鼠标、键盘、窗口大小和焦点等事件多次运行，不能把一次 `OnGUI` 当成游戏中的一帧。

`ScrollView` 的裁剪不等于数据虚拟化。若调用方仍遍历所有资源、创建控件、读取导入器，滚动区外的行仍会消耗 CPU 和分配内存。

同时区分四类成本：

| 成本 | 常见来源 | 可以怎样降低 |
| --- | --- | --- |
| 数据发现 | 场景遍历、`FindAssets`、依赖枚举 | 限定范围、按变更触发、分批扫描 |
| 数据解析 | 共享材质属性、Importer、平台格式 | 按唯一资源解析、按需缓存 |
| 结果变换 | 筛选、排序、字符串构建 | 结果缓存、明确 dirty/version |
| 控件绘制 | 行控件、`GUIContent`、布局 | 可见行范围、稳定显示内容缓存 |

### 2.3 先选工具，不急着换框架

| 工具 | 用途 | 结论边界 |
| --- | --- | --- |
| `rg` / `rg --files` | 根据窗口标题、菜单和调用关系定位源码 | 文本命中不证明运行时实际走到 |
| Git 状态、差异、历史 | 隔离既有修改、核对本轮范围 | 不代替行为测试 |
| Unity Profiler 的 Editor 采样 | 检查重绘、扫描、导入器查询和 GC | 记录采样配置；Deep Profile 可能放大成本 |
| `ProfilerMarker` | 给扫描、筛选、预览解析、绘制分别打点 | 打点本身不要遍历或格式化全表 |
| `Stopwatch` 与调用计数 | 测扫描阶段或纯算法，观察重复次数 | 避免每行日志改变被测行为 |
| Roslyn + Unity 引用程序集 | 发现语法、API、引用问题 | 仅子集编译；详见 [离线编译参考](unity-editor-script-offline-compile-verification.md) |
| 隔离的 Unity 测试工程 | 用合成资产验证窗口、导入和 Undo | 不替代正式工程及大场景回归 |
| 纯 .NET 算法检查 | 验证索引、边界和集合运算 | 无法证明 IMGUI、Importer 或许可证可用 |

现有 IMGUI 工具可以先修正数据流与绘制范围。新工具可评估 UI Toolkit `ListView` 或 `TreeView`；不因数据量大就默认重写全部界面，框架虚拟化也不会自动消除扫描和筛选成本。

## 3. 实现或排查步骤

### 3.1 从调用次数建立成本模型

用 `N` 表示匹配资源数，`V` 表示可见行数，`P` 表示平台列组数，`K` 表示每次 GUI 事件执行的全表筛选次数。

旧结构的典型成本是：

```text
每次 GUI 事件 ≈ K × N × 筛选成本
              + N × 行控件成本
              + N × P × 平台信息解析成本
```

改进结构的目标是：

```text
数据或条件变化：扫描/排序/重建筛选结果
稳定 GUI 事件：计数 O(1) + 可见行绘制 O(V)
首次看到资源：解析并缓存该资源的平台信息
后续看到资源：复用平台信息，直到相关数据失效
```

这是调用结构和复杂度的变化，不是实测加速倍数。按需缓存只在已经访问的范围内稳定，首次滚入新区域仍有元数据读取成本。

重点搜查重复发生的 `GetAssetPath`、`GetAtPath`、`GetPlatformTextureSettings`、`GetDefaultPlatformTextureSettings`、`GetAutomaticFormat`、`GetTexturePropertyNames`、`LoadAllAssetsAtPath` 和每行 `new GUIContent`。API 名称本身不等于性能问题，关键是它在哪个事件、哪个循环、以多高频率运行。

### 3.2 用同一份筛选结果驱动所有入口

将数据分为：原始结果、筛选结果、选择集合、当前可见索引范围。筛选结果负责计数、列表、全选和“应用到筛选结果”；可见索引只负责绘制。

建议的数据流：

```text
显式刷新/数据变更 -> 扫描结果 -> 排序 -> 标记筛选失效
搜索/属性条件变化 -----------------> 标记筛选失效
访问筛选结果 -> 若失效则重建 -> Count / 全选 / 批量目标 / 表格
表格 -> 计算可见索引 -> 绘制少量行 -> 按需读取预览缓存
编辑 -> 捕获目标快照 -> 执行写入 -> 数据失效 -> 重建结果
```

实现时注意：

1. `Count` 读取缓存列表的数量，不再独立遍历并匹配。
2. 搜索和属性条件真正变化时才设置 dirty；滚动、选中勾选、重绘通常不需要重新筛选。
3. 批量修改前复制目标列表。编辑可能让对象离开当前筛选，不能边遍历边重建同一列表。
4. 多页签各自维护筛选状态；共享资源集合可以统一刷新。
5. 失败的重建不应冒充成功快照；复杂工具可先构建新列表，成功后再替换旧列表。
6. 若允许外部工具持续修改资源，设计更明确的通知或版本号；不能假设窗口自己的按钮是唯一写入者。

### 3.3 用固定行高计算可见范围

下例是独立的纯 C# 算法示例，不是完整窗口。约定：输入数值有限；表头位于滚动内容内部；`scrollY` 与 `viewportHeight` 使用与行高一致的 GUI 单位；行高固定且大于零；`viewportHeight` 已扣除水平滚动条占用。

```csharp
using System;

public static class FixedHeightVisibleRows
{
    public static void GetRange(double scrollY, double viewportHeight,
        double headerHeight, double rowHeight, int count,
        out int first, out int end)
    {
        if (rowHeight <= 0 || count < 0 || headerHeight < 0)
            throw new ArgumentOutOfRangeException();

        double visibleHeight = Math.Max(0, viewportHeight);
        double maxScroll = Math.Max(0,
            headerHeight + count * rowHeight - visibleHeight);
        double y = Math.Max(0, Math.Min(scrollY, maxScroll));
        first = ClampIndex(Math.Floor((y - headerHeight) / rowHeight), count);
        end = visibleHeight == 0 ? first : Math.Max(first,
            ClampIndex(Math.Ceiling((y + visibleHeight - headerHeight) / rowHeight), count));
    }

    private static int ClampIndex(double index, int count)
    {
        return (int)Math.Max(0, Math.Min(index, count));
    }
}
```

计算结果采用半开区间 `[first, end)`；第 `i` 行的内容坐标为 `headerHeight + i * rowHeight`。用完整结果数计算内容高度，用可见范围控制循环次数。`floor` 与 `ceil` 保证顶部和底部的半行不遗漏。

接入 IMGUI 时，通常只为整个表格预留一个 `GUILayoutUtility.GetRect`，行内部改为显式 `Rect` 布局，避免不可见行仍进入 `GUILayout`。`BeginScrollView` 与 `EndScrollView` 用成对结构保护。

不要把“在 Layout 事件提前返回”当通用修复。只可在布局项已经预留、后续全部是显式 Rect 控件、且事件间控件行为已验证的子区域采用。任意跳过整个 `OnGUI` 的 Layout 会破坏 GUILayout 结构或控件状态。

| 容易遗漏的情况 | 处理思路 |
| --- | --- |
| 列表滚到底部后过滤成一项 | 先按新内容高度 clamp scroll，再算可见范围 |
| 空结果提示在表头下方 | 内容高度包含提示区域，防止提示被滚动裁剪 |
| 窗口缩小、DPI 改变 | 使用统一 GUI 坐标与实际视口，不混用屏幕物理像素 |
| 固定表头在滚动区外 | 算法不再减内部表头高度，重新定义坐标 |
| 可变行高、文本自动换行 | 使用行高前缀和与查找，或框架的动态高度虚拟化 |
| 行被裁掉后键盘焦点仍在旧控件 | 检查滚动、排序、筛选后的焦点与控件 ID；按需清理焦点 |
| 点击弹出菜单后列表变化 | 确保回调绑定资源身份，而非过时的行号 |

### 3.4 分层缓存资源信息

缓存前写清“存什么、键是什么、何时失效”。不要只添加一个 Dictionary 后就认为问题已经解决。

| 缓存层 | 典型内容 | 加载时机 | 失效条件 |
| --- | --- | --- | --- |
| 资源集合 | 资源对象、引用统计、使用者 | 扫描 | 范围、层级、依赖集合改变 |
| 筛选结果 | 排序后的匹配项列表 | 首次访问或 dirty | 搜索、条件、匹配字段、资源集合改变 |
| 基础元数据 | 资产路径、Importer、类型 | 真正需要该字段时 | 重导入、移动、删除、对象失效 |
| 显示预览 | 平台格式、Max Size、tooltip | 首次绘制相关资源 | 导入设置、相关平台配置或版本改变 |
| 扫描内共享解析 | 材质到贴图的关系 | 每个唯一材质一次 | 下一轮扫描 |

几个可迁移技巧：

- 无搜索且未按 Importer 属性筛选时，避免为了“匹配全部”读取每个资源的 Importer。
- 缓存“没有 Importer”的结果，避免对临时纹理和不支持类型重复查找；失效后允许重新查询。
- 同一 Importer 的默认平台设置可读取一次，供多个平台列复用。
- 显示字符串和 `GUIContent` 可与预览缓存一起生成；颜色、样式和内容的版本依赖分别考虑。
- 缓存对象身份可以使用会话内 Instance ID；跨域重载或持久记录使用适合子资产的稳定身份，例如 GUID 与 local file ID。
- 多个子资产可能共享路径和 Importer，必要时分成“对象元数据”和“路径级导入设置”两层；不要仅用路径标识所有子资产。
- 资源列表、筛选列表和缓存会占内存；项目全量资源浏览器需要考虑缓存上限、清理和不再访问的资源。

### 3.5 正确解析平台设置的有效值

平台预览的逻辑顺序为：读取平台设置 → 判断 override → 未覆盖时使用默认设置 → 有效格式为 `Automatic` 时调用 Unity 的平台格式解析 → 缓存展示内容。

| 状态 | Format 来源 | Max Size 来源 |
| --- | --- | --- |
| 平台覆盖启用 | 平台 format；若为 Automatic 再解析 | 平台 maxTextureSize |
| 平台覆盖关闭 | 默认 format；若为 Automatic 再解析 | 默认 maxTextureSize |
| 不存在 TextureImporter | 明确表示不适用 | 明确表示不适用 |

直接展示 `Texture.format` 通常反映已加载纹理当前格式，不能替代任意目标平台的导入配置预览。Max Size 也是导入上限，不等于当前纹理实际宽高。自动格式依赖纹理类型、压缩设置、平台支持和 Unity 版本，迁移时重新对照 Inspector。

### 3.6 用明确的事件使缓存失效

| 事件 | 适合失效的层 | 注意点 |
| --- | --- | --- |
| 搜索/属性筛选变化 | 筛选结果 | 不需要重扫场景 |
| 列宽、滚动、普通勾选 | 通常没有数据失效 | 只更新绘制或选择 |
| 当前工具编辑材质字段 | 对应筛选、相关显示 | 当前行可能因此离开结果集 |
| 纹理重新导入 | Importer/平台预览、筛选；必要时集合 | 在写入结束后更新 |
| Undo / Redo | 修改涉及的缓存 | 旧包装对象与设置可能失效 |
| 场景层级、扫描范围变化 | 资源集合及其派生数据 | 合并重复刷新请求 |
| Selection 变化 | 仅当扫描范围依赖 Selection | 普通定位不应无条件重扫 |
| 窗口重新获得焦点 | 可作为外部编辑后的兜底 | 宽泛全量刷新可能再次造成卡顿 |
| 切换到无关页签 | 保留待刷新请求 | 只在实际刷新时清除请求 |
| 关闭/域重载/资源销毁 | 释放或重建 | 订阅与退订成对 |

dirty flag 的关键是“被处理后再清除”。先清除请求，再判断当前页签不适合处理，会把刷新需求丢掉。

窗口级 `OnProjectChange`、`OnHierarchyChange`、Undo 和焦点恢复是可用的基础策略，但不承诺捕获所有程序化属性变化。对外部实时编辑、资源删除或平台切换，按实际消费者补充失效来源；先考虑局部通知，避免仅为刷新列表新增全局重导入 Hook。

资源规模继续增长时，可以把“集合失效”“筛选失效”“元数据失效”拆开。事件只标记，后续调度合并处理；长扫描按时间预算分批运行。Unity 对象、场景、AssetDatabase 与 Importer 的访问保持在 Unity 支持的线程上下文中；纯值数据的计算才单独考虑后台执行。

### 3.7 共享解析去重不改变引用统计

“唯一资源列表”与“资源被引用的次数”是两条数据链。可以只解析一次共享材质的纹理属性，但每次遇到该材质引用仍需累计其纹理引用。

示例：四个 Renderer 共用同一材质，材质有一个纹理属性指向同一贴图。列表中是一个材质和一张贴图，引用数仍可为四。若同一贴图绑定材质的两个纹理属性，按引用边计数可能为八；这不等于八个独立 Renderer。

扫描结果的统计定义应写清：是否按 Renderer 材质槽、材质属性、TerrainLayer 属性累计，是否去重父子选择重叠。迁移时不要以“优化”为由悄悄改变计数单位。

### 3.8 排查无花括号的分支错误

以下片段是故意展示的错误模式，仅用于解释 C# 的 `else` 绑定规则：

```csharp
if (showMaterials)
    foreach (var item in materials)
        if (Matches(item)) count++;
else
    CountTextures();
```

`else` 绑定最近一个尚未配对的 `if (Matches(item))`，不是缩进上看起来对应的外层判断。结果可能是纹理页永远不计数，材质不匹配时反而走纹理分支。

修正思路：给外层分支和复杂循环加明确花括号；计数、全选、批处理三条相邻入口一起检查；优先用缓存结果消除重复实现。这类问题编译可以通过，验证需要覆盖两个页签、空列表、匹配与不匹配项。

### 3.9 保留选择、写入与恢复边界

全选作用于完整筛选列表，不能改成可见行循环。选择集合用对象身份维护，行号仅是显示位置；排序和筛选后行号可能指向另一对象。

对 Importer 修改，常见做法是在 GUI 输入时捕获目标路径集合、字段和值，再通过受控执行入口或 `EditorApplication.delayCall` 执行：

1. 执行时再次解析并校验目标 Importer。
2. 比较原值，跳过未变项。
3. 按目标类型登记 Undo，然后设置字段。
4. 对必要目标执行 `SaveAndReimport`。
5. 在结束或异常收尾时使相关缓存失效。

延迟回调只是推迟时机，不是后台线程，也不会自动缩短导入耗时。回调还需要考虑窗口关闭、域重载、重复提交和执行互斥。批量路径去重可减少同一 Importer 因多个子资产而重复导入。

`Undo.CollapseUndoOperations` 合并撤销记录，`try/finally` 保证收尾；两者都不代表异常时自动回滚。大型任务另行设计逐项结果、失败后继续或中止、取消安全点和恢复方案。使用 `StartAssetEditing` 前确认实际导入行为与配对清理，不直接套在任意 `SaveAndReimport` 循环外。

## 4. 风险与不适用边界

### 4.1 虚拟化解决不了的剩余工作

- 首次扫描、全项目加载、排序依旧可能很慢；显示优化与发现优化分开评估。
- 搜索或切换筛选仍可能需要遍历完整集合；冷缓存的属性筛选可能首次读取大量 Importer。
- 首次滚入一批资源仍需要解析平台信息；必要时预算化预取，但避免预取全表。
- 只对行做虚拟化时，横向不可见列可能仍被绘制；列数很多且单列昂贵时再评估列裁剪。
- 在焦点变化时清空全部缓存是可靠性与性能的折中，可能造成重复扫描；它不是增量失效方案。
- 显示缓存依赖对象有效性和通知完整性；过期显示与漏更新也是缺陷。

### 4.2 不把实现选择推广成绝对规则

| 不宜直接推广的结论 | 更准确的表述 |
| --- | --- |
| “所有 OnGUI 读取都很慢” | 先量调用频率与成本，优先减少重复且昂贵的读取 |
| “任何 Editor 工具都需要缓存” | 缓存引入失效和内存成本，小规模一次性查询未必需要 |
| “有 ScrollView 就只画可见行” | 裁剪与调用方跳过不可见行是不同机制 |
| “缓存后每次绘制零分配” | GUI 控件、字符串和其他字段仍可能分配，需实测 |
| “虚拟化后扫描也变快” | 绘制量下降，不代表扫描、排序和资源加载量下降 |
| “延期执行等于异步加速” | delayCall 仍在 Editor 执行，导入仍可能阻塞 |
| “有 Undo 就能完整回滚” | 具体资源类型、重导入及外部副作用分别验证 |
| “编译和算法通过就证明窗口流畅” | 还缺真实宿主、代表性数据和操作验证 |

## 5. 验证与回退

### 5.1 按结论选择证据

| 层级 | 操作 | 通过条件 | 不能宣称 |
| --- | --- | --- | --- |
| 源码与范围 | 检查调用链、差异、编码、读写边界 | 只改预期模块，路径与行为契约清楚 | 已测性能 |
| 子集编译 | 编译相关 partial 文件，引用匹配的 Unity 程序集 | 无编译错误，记录编译器和引用 | 全项目编译通过 |
| 纯算法 | 空表、半行、底部、缩放、过滤后 clamp、大数索引 | 索引有界、不漏可见项、数量受视口约束 | 一百万真实纹理已运行 |
| 独立 Unity | 合成资源、Importer、窗口事件、Undo | 无 GUI 异常，结果与设置正确 | 正式项目所有资源均正常 |
| 真实工程 | 相同场景和窗口尺寸 A/B | 功能一致，热点耗时与分配符合预算 | 未采样场景也有相同比例收益 |

算法层建议检查 `0 <= first <= end <= count`；每个与视口相交的行都在范围内；固定正行高时数量不超过约 `ceil(viewportHeight / rowHeight) + 1`。零高度视口可以定义为空范围；超大高度和浮点精度另设边界，不把数学上有界等同于 IMGUI 能承载任意规模。

本文 §3.3 的独立示例在文档整理时已完成编译及 2000 组检查，覆盖不同表头/行高参数、零高度视口、滚动 clamp 和可见行包含性。它显式处理零高度并内置 clamp，与项目原函数不是逐字副本；这些结果只证明示例的算法行为，不补足项目 Profile 中的 Unity 宿主验证缺口。

### 5.2 代表性操作清单

- [ ] 首次打开、重复重绘、快速滚动、滚到最后一行、横向滚动、列宽调整正常。
- [ ] 资源范围、未激活开关、场景范围与原契约一致。
- [ ] 搜索成零项/一项后滚动位置正确；空结果提示完整可见。
- [ ] 名称、路径、类型、Importer 布尔值、Filter/Wrap 筛选各自正确。
- [ ] 计数、可见内容、全选数量和批量目标来自同一筛选快照。
- [ ] 筛选隐藏的已选项是否继续参与“应用到已选”，与约定一致。
- [ ] 无 Importer、临时对象、子资产、丢失 Shader、资源删除和移动可处理。
- [ ] 平台覆盖、默认回退、Automatic、实际大小与 Max Size 逐项对照。
- [ ] 修改、重新导入、Undo/Redo、焦点恢复、切页后缓存正确更新。
- [ ] 行控件焦点、弹出菜单、定位按钮、滚动条拖动不误操作别的行。
- [ ] 关闭窗口、域重载、延迟回调和批量失败有明确清理/恢复结果。
- [ ] 共享材质去重未改变引用统计；父子重叠选择按约定处理。

### 5.3 记录可比较的性能结果

比较时固定 Unity 版本、场景、资源数、唯一材质数、显示分辨率、窗口尺寸、筛选和列数。分别测冷启动、温缓存静止重绘、搜索、滚动、焦点恢复和批量应用；记录重复次数、时间分布和 GC，而不只记一个平均值。

没有旧版数据时，可以报告热点调用数已减少、缓存是否复用以及算法复杂度；不要编造“提升百分比”。没有宿主许可证或权限时，保存具体失败信息，完成可进行的检查，明确 Unity 行为待验；进程成功启动不等于测试入口已经执行。

### 5.4 回退与下一次开发复用

按 `TOOL-CMP-01` 保留改动前源码与代表性结果。性能修改和资产编辑分开回退；回退窗口代码不会恢复此前已经重导入的贴图设置。对于部分成功的批处理，按目标清单与版本管理恢复，不对整个工作区做无差别撤销。

下一次开发可以按以下顺序使用本文：

1. 冻结范围、统计、筛选、选择和写入语义。
2. 确认卡顿阶段，并给扫描、筛选、元数据和绘制分别取证。
3. 优先消除重复工作，再加入可见行绘制和必要缓存。
4. 画出缓存失效表，检查外部编辑与后台页签。
5. 用同一筛选快照驱动计数、全选与批量目标。
6. 完成编译、算法、宿主和代表性场景验证，分别报告状态。

更多通用结构见 [工具实现模式](tool-development-patterns.md) 和 [工具集成检查](tool-integration-checklist.md)；项目字段和历史限制只记录在对应 Profile。
