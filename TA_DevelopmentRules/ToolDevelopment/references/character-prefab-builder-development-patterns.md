# Unity 角色 Prefab 生成器开发经验参考

> 类型：REFERENCE；适用范围：Unity Editor 中从 FBX、Prefab 或流程配置生成角色 Prefab 的工具；使用前提：必须以目标工程的 Unity 版本、资产结构、导入设置、Prefab 消费者和实际验证结果重新确认。

## 1. 适用场景

本文总结角色 Prefab 生成工具中最容易反复踩坑、也最适合迁移到其他资源生成工具的工程方法：

- 从 FBX 生成基础角色 Prefab，并可选生成外置 Mesh、材质引用、LOD 和动画控制器。
- 从前一步生成的 Prefab 再嵌套生成战斗、展示或 Timeline 专用外层 Prefab。
- 重新生成时保留手工配置、组件、节点、材质引用和第三方组件缓存。
- 处理 SubMesh 与材质槽数量变化、LOD 双来源、模型坐标轴重建和临时 ModelImporter 设置。
- 用户先删除 Prefab 后重新生成时，保持原资产 GUID。
- 将一次问题沉淀成可迁移的工具架构、排查步骤、验证矩阵和规则候选。

本文只讲实现模式与排查方法。项目的真实目录、菜单、类名、配置字段、Unity 版本和资产 GUID 应记录在项目 Profile，不应直接复制为通用规则。

## 2. 前提与依赖

### 2.1 先冻结资产契约

开始开发或修复前，先写清以下契约：

| 契约项 | 需要确认的内容 |
| --- | --- |
| 输入 | FBX、源 Prefab、流程配置、选中对象、目录范围或批量清单。 |
| 输出 | Prefab、外置 Mesh、可选 Controller、坐标重建 Profile、日志和登记资产。 |
| 命名 | 源模型、品质、角色编号、步骤 Key、外层 Prefab 和 Timeline Prefab 的命名模板。 |
| 覆盖 | 已有 Prefab 是全量刷新、增量补充、只读检查，还是明确拒绝覆盖。 |
| 兼容 | 历史配置字段、旧资产、嵌套 Prefab 连接、材质数组、组件参数和 `.meta`。 |
| 可撤销 | 是否支持 Undo；批量写入失败时依赖 Git、快照、临时目录还是事务回滚。 |
| 验证 | Unity 编译、Editor 行为、资产引用、GUID、重开 Prefab、运行时或视觉结果。 |

如果其中一项没有答案，先将它记录为待确认边界，不要在代码里用隐式默认值替代。

### 2.2 Unity 资产身份是路径与 `.meta` 的组合

Unity 的资产身份不是文件名。常见关系如下：

| 操作 | GUID 行为 |
| --- | --- |
| 同路径覆盖保存 | 通常沿用原 `.meta`，GUID 保持。 |
| Unity Project 窗口删除资产 | 通常连同 `.meta` 一起删除，旧 GUID 丢失。 |
| 删除文件但保留 `.meta` | 重新导入时可能继续使用原 GUID。 |
| 复制文件并复制 `.meta` | 可能产生 GUID 冲突，不能作为常规复制方式。 |
| 新路径生成同名文件 | 会生成新 `.meta` 和新 GUID。 |

因此，“重新生成是否保持 GUID”必须拆成两个问题：保存时是否沿用原路径，以及旧 `.meta` 是否仍可恢复。只依赖同名或 `AssetDatabase.LoadAssetAtPath` 不能解决删除后重建。

## 3. 总体工作流程

### 3.1 加载上下文

工具入口先读取选中资产、路径解析结果、配置资产、目标步骤和已有输出。不要在 `OnGUI` 绘制阶段直接执行生成、删除、重导入或长时间扫描。

建议把流程拆成：

1. `Input`：收集选择、配置和用户选项。
2. `Resolve`：解析角色类型、编号、品质、源资产、输出目录、步骤依赖和目标路径。
3. `Validate`：校验路径、命名、类型、依赖、冲突、覆盖策略和可生成性。
4. `Plan`：生成可观察的执行计划，包含目标、动作、风险、跳过和输出。
5. `Execute`：只消费已校验的计划，逐项记录成功、失败和跳过。
6. `Save`：统一处理 Prefab、Mesh、Profile、GUID 和导入刷新。
7. `Verify`：读取保存后的真实资产，检查引用、层级、GUID、材质槽和可重开性。

### 3.2 冻结生成步骤

复杂流程建议将每个步骤解析成不可变或准不可变的 `ResolvedBuildStep`，至少保存：

- 步骤 Key、顺序、显示名和启用状态；
- 输入源类型：Model FBX 或 Prefab From Step；
- 主源和可选低模源路径；
- 输出目录、Prefab 名称、根节点名称和最终路径；
- 是否已存在、是否可生成、错误原因；
- 覆盖模式：全量刷新或保留已有并补充；
- Mesh、LOD、组件模板、Prefab 模板、层级和 Cast Shadows 配置。

解析阶段完成后，执行阶段不要重新猜路径、品质或配置。这样可以避免“预览显示一个目标，实际写入另一个目标”的问题。

### 3.3 处理步骤依赖

当一个步骤依赖另一个步骤生成的 Prefab 时，用 `BuildSession` 保存：

- `StepsByKey`：步骤 Key 到解析结果的索引；
- `BuiltPrefabPaths`：已生成步骤的缓存，避免重复生成；
- `InProgressKeys`：检测循环依赖；
- 源 FBX 导入设置快照；
- 坐标重建或其他临时 Profile 的路径缓存。

递归构建时先检测缓存，再检测步骤是否存在、启用和可生成，最后加入进行中集合。无论成功或异常，都要在 `finally` 移除进行中标记。

## 4. 生成模式与资产兼容

### 4.1 Model FBX 与 Prefab From Step 分开

Model FBX 步骤关注模型导入、外置 Mesh、材质槽、骨骼、LOD 和坐标；Prefab From Step 步骤关注嵌套连接、外层结构、模板和组件。两者可以共用保存与校验基础设施，但不要把 FBX 导入逻辑复制到 Prefab 步骤。

### 4.2 全量刷新与增量补充分开

全量刷新适合基础 Prefab：

- 以当前源 FBX 或源 Prefab 重新建立主体结构；
- 按稳定层级路径恢复明确声明要保留的子节点和组件；
- 对已有材质、阴影状态和允许保留的配置执行显式合并；
- 未声明保留的旧节点可以被移除。

增量补充适合战斗、展示和 Timeline 外层 Prefab：

- 先加载已有 Prefab 内容；
- 只补充缺失的源实例、模板对象或组件；
- 已有手工对象和参数优先保留；
- 对同源嵌套 Prefab 继续保持 Prefab 连接。

不要让一个“是否存在”的布尔值同时决定刷新、增量和 GUID 行为。覆盖策略、资产身份和内容合并属于三个独立维度。

### 4.3 保存 Prefab 的职责边界

将所有 Prefab 写入集中到一个保存适配层，例如：

```csharp
internal static GameObject SavePrefab(GameObject root, string path)
{
    // 校验路径、准备 meta/GUID、调用 SaveAsPrefabAsset、导入并验证。
}
```

主体构建代码只负责得到内存中的 `GameObject`，不要在多个分支直接调用 `PrefabUtility.SaveAsPrefabAsset`。集中保存层才能统一处理：

- 原路径覆盖；
- 删除后 GUID 恢复；
- 失败后的清理；
- `AssetDatabase.ImportAsset`；
- 实际 GUID 回读；
- 统一日志和错误信息。

## 5. 外置 Mesh、材质槽与 LOD

### 5.1 外置 Mesh 是导入预设的稳定落点

如果临时修改了 FBX 的 ModelImporter 设置，但 Prefab 仍引用 FBX 内部 Mesh，恢复导入设置后内部子资产可能重新生成，导致法线、切线、焊接、优化或坐标结果变化。

因此，导入预设、平滑法线或坐标重建链路通常应将目标 Mesh 外置为独立资产，并让 Prefab 引用外置 Mesh。外置 Mesh 更新时尽量沿用原路径和对象身份，避免无意义替换 `.meta` 或破坏引用。

### 5.2 材质数组按索引合并

当源 FBX 的 SubMesh 数量变化时，旧 Prefab 的材质数组不能直接覆盖新数组。可迁移的合并策略是：

| 旧材质数组 | 源材质数组 | 处理 |
| --- | --- | --- |
| 无有效材质 | 任意 | 使用源数组。 |
| 重叠索引存在旧材质 | 任意 | 保留旧材质。 |
| 新增索引 | 源数组有值 | 从源数组补入。 |
| 新增索引 | 源数组为空 | 保留空槽并报告源数据问题。 |
| 源数组变短 | 任意 | 只截掉超出源长度的尾部槽位，不重排前面索引。 |

不要按材质名排序、不要凭 Renderer 名称猜槽位、不要复制前一个槽位，也不要自动新建材质来掩盖 FBX 数据错误。材质槽策略应抽成无窗口的纯函数，并覆盖增槽、减槽、等槽和空引用测试。

### 5.3 LOD 必须分别处理

LOD0 与 LOD1 可能来自不同 FBX，必须分别实例化源模型、读取 Renderer、生成 Mesh 和材质数组，再映射到目标骨架。不能把 LOD0 的材质数组、SubMesh 数量或路径缓存复用于 LOD1。

## 6. 临时导入设置与异常恢复

### 6.1 原值快照

第一次接触每个源 FBX 时捕获完整公开导入设置，以规范化资产路径为键。后续同一构建会话重复使用该快照，避免步骤之间互相读取临时值。

### 6.2 临时套用

只修改明确勾选的字段；未勾选字段从快照恢复或继续继承源值。需要顶点读取时可以临时强制 `Read/Write`，但该要求不应永久污染源 `.meta`。

执行顺序通常是：

1. 捕获原始设置。
2. 计算目标设置并仅写入差异。
3. `SaveAndReimport()`。
4. 生成 Mesh、Prefab 和依赖资产。
5. 在外层 `finally` 恢复所有源设置。
6. 对恢复失败逐项记录并在最后汇总。

恢复逻辑不能只放在正常返回路径。失败、取消、异常、生成中断和窗口关闭都必须进入同一清理路径。

## 7. 手工内容与第三方组件恢复

### 7.1 明确所有权

重新生成前先区分：

- 源 FBX 固有节点和组件；
- 生成器拥有的节点和组件；
- 用户手工新增的节点和组件；
- 第三方插件产生的序列化缓存。

只对明确声明可恢复的对象做迁移。不能用“保留所有未知对象”代替所有权分析，否则源结构变化时会累积脏节点。

### 7.2 稳定定位

优先使用稳定层级路径、组件类型、同类型序号和源 Prefab GUID。对于嵌套 Prefab，保存源 GUID 并通过 `PrefabUtility.InstantiatePrefab` 恢复连接；对于外部材质、Mesh、Controller 和纹理，使用 GUID 加 local fileID，而不是只存文件名。

### 7.3 快照与事务

复杂模块可以采用：

1. 生成前捕获快照；
2. 分析新旧层级和组件差异；
3. 生成 Dry Run 计划；
4. 只执行通过校验的恢复模块；
5. 保存后重新采集实际结果；
6. 对第三方缓存执行显式重建；
7. 失败时依赖快照、版本控制或临时副本回退。

没有可靠稳定身份时宁可阻断恢复，也不要静默挂错组件或把引用写到同名但不同对象上。

## 8. 删除后重建的 GUID 保持

### 8.1 问题根因

普通的同路径覆盖使用 `SaveAsPrefabAsset` 可以沿用 `.meta`。但用户先删除 Prefab 时，旧 `.meta` 也被删除，Unity 后续生成的新文件没有任何依据恢复旧 GUID。

这不是 `SaveAsPrefabAsset` 是否“覆盖”的问题，而是旧资产身份已经不存在。

### 8.2 可迁移实现

增加一个项目内、可版本控制的 GUID 登记资产，记录：

```text
PrefabPath -> Guid
```

保存适配层执行以下顺序：

1. 读取当前路径的 GUID；存在则登记并继续。
2. 当前路径不存在时读取仍存在的 `.meta`；存在则登记并继续。
3. `.meta` 不存在时查询登记表。
4. 找到登记 GUID 后，确认该 GUID 没有被其他路径占用。
5. 在 Prefab 保存前恢复目标 `.meta` 的基本 GUID 内容。
6. 调用 `PrefabUtility.SaveAsPrefabAsset`。
7. 强制导入并回读 `AssetDatabase.AssetPathToGUID`。
8. 若 GUID 不一致，停止并报错；不要静默接受新 GUID。
9. 保存成功后更新登记表。

登记资产必须和 `.meta` 一起进入版本控制，并且不能放在会被忽略、自动生成或多人各自独立维护的位置。

### 8.3 GUID 冲突保护

登记表中的 GUID 可能已经被其他资源占用，例如资产被移动、分支合并或手工复制 `.meta`。恢复前应通过 `AssetDatabase.GUIDToAssetPath` 检查：

- 空路径：可以恢复；
- 同一路径：可以继续；
- 其他路径：阻断并报告冲突。

不要为了“让生成成功”而覆盖其他资源的 `.meta`。GUID 冲突属于资产安全错误，不属于可忽略警告。

### 8.4 不能恢复的情况

以下情况无法可靠恢复原 GUID：

- Prefab 从未被工具登记过；
- 登记资产和旧 `.meta` 都丢失；
- 登记表记录被错误覆盖；
- 旧 GUID 已经合法地分配给其他资源；
- 目标路径或资产语义已经改变，无法证明是同一资产。

这时应生成新 GUID，并在日志或迁移报告中明确指出引用可能需要修复。

## 9. 常见问题与排查决策表

| 现象 | 首先检查 | 常见根因 | 处理方式 |
| --- | --- | --- | --- |
| 删除后重建 GUID 变化 | `.meta` 是否被删除、登记表是否存在 | Unity 已无法知道旧身份 | 从登记表恢复 `.meta`，冲突则阻断。 |
| 同名 Prefab 被错误引用 | GUID 与路径，不看文件名 | 文件名不是资产身份 | 使用 GUID/local fileID 或 AssetDatabase 查询。 |
| Mesh 有两个 SubMesh 但 Prefab 只有一个材质槽 | 源 Renderer 数组、目标 `m_Materials`、写入顺序 | 旧材质数组直接覆盖新数组 | 按索引合并并测试增减槽。 |
| 重新生成后手工组件丢失 | 覆盖模式和快照入口 | 全量刷新没有恢复计划 | 使用增量模式或生成前捕获快照。 |
| 组件恢复到了错误骨骼 | 稳定路径、类型序号和父节点映射 | 只按名称或模糊搜索 | 先分析映射，歧义时阻断。 |
| LOD0 正常、LOD1 错误 | LOD1 独立源、材质数组、目标路径 | 复用了 LOD0 数据 | 每个 LOD 独立解析、生成和验证。 |
| 预设生成结果恢复导入后变化 | Prefab 是否仍引用 FBX 子资产 | 临时导入值没有稳定落到外置 Mesh | 生成外置 Mesh，再恢复源导入设置。 |
| 异常后 FBX 仍保留临时设置 | 外层 `finally`、每个 importer 快照 | 恢复只写在正常路径 | 将恢复放在构建会话统一清理阶段。 |
| 工具窗口无报错但资产不对 | 保存后重新读取的 Prefab 与 GUID | 只验证内存对象或 UI 预览 | 重新导入、重开 Prefab、读取真实序列化结果。 |
| CLI 编译通过但 Unity 不工作 | Unity Editor 编译和导入日志 | 宿主 API、序列化或导入行为未验证 | 把 CLI 当补充，必须做宿主内验证。 |

## 10. 验证矩阵

### 10.1 静态验证

- 检查新增脚本的 UTF-8、命名空间、程序集和 Editor-only 边界。
- 搜索所有 Prefab 保存入口，确认没有遗漏的直接保存旁路。
- 检查目标路径、登记路径、`.meta` 和 GUID 的唯一性。
- 检查 `git diff --check`、文档链接、尾随空白和序列化字段名。
- 检查 GUID 登记表的路径数、GUID 数、重复 GUID 和当前 `.meta` 一致性。

### 10.2 Editor 行为验证

至少执行以下矩阵：

| 场景 | 通过条件 |
| --- | --- |
| 新路径首次生成 | Prefab 可加载，路径和引用正确，登记表新增 GUID。 |
| 已有 Prefab 同路径刷新 | 内容按刷新契约更新，GUID 不变。 |
| 已有 Prefab 增量更新 | 手工内容保留，源嵌套连接有效，GUID 不变。 |
| 删除 Prefab 和 `.meta` 后重建 | 登记资产存在时 GUID 恢复；重建后回读与旧值一致。 |
| GUID 已被其他资源占用 | 阻断保存，不覆盖其他资源，错误可定位。 |
| 源 FBX 导入预设 | 生成后源导入设置恢复，外置 Mesh 保持预设结果。 |
| SubMesh `1 → 2` | 旧索引材质保留，新索引从源补入。 |
| SubMesh `2 → 1` | 前部索引保留，只移除尾部槽位。 |
| LOD0/LOD1 不同槽位 | 两路分别读取和写入，互不污染。 |
| 异常或取消 | 临时设置恢复，已完成和未处理项有明确汇总。 |
| Unity 重开和重新导入 | Prefab、Mesh、材质、Controller 和嵌套引用仍有效。 |

### 10.3 运行时或视觉验证

如果 Prefab 被 Timeline、角色战斗、动画或渲染系统消费，还需在实际消费者中验证：

- Animator、Avatar、Controller 和 Root Motion；
- LOD 切换、Bounds、骨骼姿态和坐标轴重建；
- 材质槽、阴影开关、第三方组件和挂点；
- Timeline 外层 Prefab 的嵌套连接和绑定；
- 多分辨率、重开场景、Domain Reload、Player 或资源包加载。

窗口能打开、Console 没有异常不能替代这些验证。

## 11. 回退与交付

批量 Prefab 保存通常没有逐项 Unity Undo。交付前应说明：

- 哪些文件和资产被修改；
- 哪些输出可以通过 Git 回退；
- 哪些源 FBX 导入设置会恢复；
- 哪些手工模块通过快照恢复；
- 哪些项目资源必须提交 `.meta`；
- 哪些验证在 Unity 内完成，哪些只完成静态检查；
- 哪些异常需要人工处理而不是自动覆盖。

当保存适配层检测到 GUID 不一致、登记表损坏、资产冲突或关键引用丢失时，应停止当前目标，不把结果标记为成功。对于已经生成但无法证明身份一致的资产，先保留日志和临时副本，再由用户决定迁移或删除。

## 12. 可迁移的工具设计清单

- 输入、解析、校验、计划、执行、保存和验证分层。
- 所有资产写入集中到可测试的 Assets/IO 适配层。
- 覆盖模式、内容合并、GUID 身份和回滚策略独立建模。
- 路径、类型和 GUID 是事实来源，文件名只用于显示和命名约束。
- 旧数据按稳定路径、组件类型、GUID/local fileID 和显式快照恢复。
- 外置资源用于承接临时导入设置和可重复生成结果。
- LOD、步骤依赖和嵌套 Prefab 各自维护输入与缓存，不跨职责复用隐式状态。
- 保存后重新导入并读取真实资产，不只检查内存对象。
- 任何删除、覆盖、替换和迁移都提供预览、日志、失败边界和回退方式。
- 每次已验证的问题都按“现象 → 根因 → 修正 → 适用范围 → 验证 → 回退”沉淀，未验证经验保留为 Profile 候选。
