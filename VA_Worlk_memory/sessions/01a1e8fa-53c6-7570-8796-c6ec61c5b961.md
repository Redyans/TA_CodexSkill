- **运行时收集的 SVC 白名单**：记录游戏运行过程中观察到的完整变体组合。

如果按我建议的方式实现，**白名单文件本身不会被修改**。即使运行时收集到了带阴影关键字的 BaseLit 组合，构建时也会把它剔除。

例如白名单里有两条：

```text
组合 A：_USE_BASE_HSV _MAIN_LIGHT_SHADOWS _SHADOWS_SOFT
组合 B：_USE_BASE_HSV
```

构建时将 `_MAIN_LIGHT_SHADOWS` 和 `_SHADOWS_SOFT` 加入 BaseLit 的强制剔除规则：

- **组合 A**：包含禁止的关键字，剔除。
- **组合 B**：没有禁止的关键字，允许继续与白名单匹配。

**这里剔除的是整条变体组合，不是从组合 A 里去掉两个关键字、自动变成组合 B。** 因此，需要确保白名单中存在对应的无阴影组合，或者明确设计可靠的保留策略。

构建判断顺序建议是：

```text
Unity 生成候选变体
       ↓
包含 BaseLit 禁用关键字？
  是 → 剔除整条变体
  否 → 继续检查 SVC 白名单
       ↓
白名单精确匹配，或在允许范围内执行回退
```

现有裁剪器的回退逻辑也必须受同一条强制剔除规则约束，不能在没有精确匹配时又把阴影变体保留回来。并且，运行时仍开启 URP 阴影关键字时，是否正确使用无阴影组合，需要在 Android/iOS 构建中验证。

所以答案是：**白名单里的记录还在，但打包时这些记录对应的变体会被强制剔除。** 重新收集白名单也不会覆盖剔除规则。

## 78. Codex

时间：2026-11-18T06:15:00.834Z

`INSTANCING_ON` 是 **GPU Instancing（GPU 实例化）变体**，让多个相同 Mesh、相同材质的对象可以合并绘制，主要影响 CPU 开销和 Draw Call 数，不是阴影开关。

当前 SVC 里它只出现在 BaseLit 的 `ShadowCaster`（`PassType 8`）变体中。不过 shader 多个 Pass 都声明了 `multi_compile_instancing`，所以构建强制剔除它时，可能同时失去 BaseLit 其他 Pass 的实例化变体。431 个 BaseLit 材质中有 3 个启用了实例化变体支持；这不能单独证明场景里实际用到了 GPU Instancing。

因此，**如果目标只是去掉实时阴影，建议保留 `INSTANCING_ON`**。剔除它通常不会改变普通对象的颜色，但会让实例化绘制失效或退化，增加 CPU 和 Draw Call；若这些对象参与实时投影阴影，阴影 Pass 的行为也可能受影响。确认项目不依赖这些材质的 GPU Instancing、并接受性能变化后，再把它加入强制剔除规则。
